The practice project

From unit 3 on, one small project grows with each unit: a sync service. It pulls records from an outside API into PostgreSQL, keeps them current and shows their status. An example of the records is the issues of a public repository.

The practice API is the GitHub REST API. It is free and it returns results in pages. Its limit without a token is 60 requests an hour, which is low enough to reach on purpose.

Units 0 to 2 use the notes application of Lab 1.

If you use an AI assistant
  1. Lab steps: Make the first attempt without the assistant. Predict, run, read the error. Then ask the assistant to explain, not to fix.
  2. Build tasks: The assistant writes. You write the specification and the checks first, ask for one change at a time, and read every changed file before you run it.
  3. By hand: All SQL in unit 4, and one small edit in every lab.
  4. Debugging: State your own guess at the cause before you ask.
  5. Setup: Use a mode that asks before it runs commands, lab-only credentials, and a rule that blocks reading .env.

Every Do step in units 0 to 2 can be done without an assistant.

How the labs were checked

Lab 1 and Lab 2 were run in containers on Linux on October 11, 2026, with substitute images. The image build, the official images and Windows with WSL have not been run. If a step behaves differently on your machine, note the step and the exact output.

EElectivesPlanned

Topics for a larger system. They are added when the project needs them and are not part of the first pass.

Planned labs

  • Queues: RabbitMQ beside arq. Run RabbitMQ's work queue tutorials, stop a worker during a task, and watch the broker hand the message to another worker.
  • Queues: SQS behavior with ElasticMQ. See a visibility timeout and a dead-letter queue on an SQS-compatible server in a container, with no AWS account.
  • Queues: queue depth as a scaling signal. Print the queue length while jobs arrive faster than one worker finishes them, and decide from the numbers when to add a worker.
  • Connection pooling with PgBouncer. Run PostgreSQL out of connections under load, then put a pooler in front of it.
  • Read replicas and replication lag. Add a streaming replica, send reads to it, and measure how often a read misses a recent write.
  • Partitioning and sharding. Partition a table inside PostgreSQL, then distribute it across nodes and choose the key.
  • Schema changes without downtime. Check a migration for locking problems, apply an expand-and-contract change, and rehearse a cutover between two databases.
  • WebSockets and server-sent events behind a proxy. Put nginx in front of the API and see the idle timeout and buffering that do not show up on localhost.
  • Load and fault injection. Generate load, add latency and dropped connections between services, and record what fails first.
  • CDN and HTTP caching. Put a CDN in front of the API and read its cache status header. Needs a domain name.

Overview

Where Stage 10 sits

Stage 10 starts once the application is live. It takes the running servers and the backups from Stage 9, the operating requirements from Stage 1, the version table from Stage 3 and the roles from Stage 7, and produces a runbook of routines, each with an owner.

Basics

Operations terms

  • Retention period. How long a kind of record or log is kept before it is deleted.
  • Error tracker. A service that collects application errors, groups them and alerts people.
  • Monitoring. Regular measurements of the servers and services, such as disk space and queue length, with alerts when a value passes a limit.
  • journald and logrotate. journald keeps the output of systemd services. logrotate renames, compresses and deletes log files that programs such as nginx write.
  • Runbook. The written steps for a routine task or an incident, so that anyone on the team can carry them out.
  • Incident. An event that stops users working or puts data at risk, such as an outage, data loss or an exposed secret.
  • Fix forward. Correcting a problem with a new release instead of going back to the previous one.
  • Patch. A release that fixes bugs or security problems without adding features.
  • Rotation. Replacing a secret with a new one, then revoking the old one.

Stages 1, 3, 7 and 9 supply the requirements, versions, roles and running servers, and the Inputs table adds the settings from Stage 4 and the Redis broker from Stage 8. The nine routines turn them into runbook sections, each with an owner, and the settings on the servers and in the repository.

Step 1 of 9

Logs and retention

Each kind of log is kept for its Stage 1 period by the tool that already holds it: journald for service output, logrotate for nginx, and a nightly job for the audit and send records in the database. Logs are not deleted before the required period ends, and are not kept long after it (Sources 64 and 125).

The retention job. deploy/retention.py:
Python
"""Delete audit and send records older than their retention period.

Runs nightly at 03:30 from user-notices-retention.timer, as the database role
usernotices_owner, with MIGRATION_DATABASE_URL from /etc/user-notices/migrate.env.
The application's role cannot delete these rows (Stage 7), so this job must use
the owner role.
"""
import os
import sys

import psycopg

# Stage 1: audit records and send records are kept 2 years.
DELETES = {
    "audit_log": (
        "DELETE FROM audit_log "
        "WHERE occurred_at < now() - interval '2 years'"
    ),
    "notice_messages": (
        "DELETE FROM notice_messages m USING notices n "
        "WHERE m.notice_id = n.id AND n.send_at < now() - interval '2 years'"
    ),
}


def main() -> int:
    # The setting holds an SQLAlchemy URL; psycopg takes the plain form.
    url = os.environ["MIGRATION_DATABASE_URL"].replace(
        "postgresql+psycopg://", "postgresql://", 1
    )
    # One transaction: both deletes are kept, or neither is.
    with psycopg.connect(url, application_name="user-notices-retention") as conn:
        for table, sql in DELETES.items():
            deleted = conn.execute(sql).rowcount
            print(f"{table}: {deleted} rows older than 2 years deleted")
    return 0


if __name__ == "__main__":
    sys.exit(main())

Watch for
    

  • A SystemMaxUse= that is too small. journald then deletes the oldest files before 30 days. It also deletes early when free disk space falls below SystemKeepFree=.
    • 

  • The journal's copy in /var/log/syslog. # app/errors.py
from pathlib import Path
import re
import socket

import sentry_sdk

from app.settings import Settings

# On the servers this file is /opt/user-notices/releases/1.4.0/backend/app/errors.py,
# so the release folder's name is the version that deploy.sh installed.
VERSION = Path(__file__).resolve().parents[2].name

# PostgreSQL adds the rejected row to some error messages, and that row can hold a
# phone number: "DETAIL:  Failing row contains (..., +15550001234, ...)".
FAILING_ROW = re.compile(r"\n?DETAIL:.*", re.DOTALL)


def drop_row_details(event, hint):
    for exc in event.get("exception", {}).get("values", []):
        if exc.get("value"):
            exc["value"] = FAILING_ROW.sub("", exc["value"])
    return event


def init_error_tracking(settings: Settings) -> None:
    """Send unhandled errors to GlitchTip. Does nothing when SENTRY_DSN is empty."""
    if not settings.sentry_dsn:
        return
    sentry_sdk.init(
        dsn=settings.sentry_dsn,
        # The server's host name tells live and sandbox apart without another setting.
        environment=socket.gethostname(),
        release=f"user-notices@{VERSION}",
        send_default_pii=False,          # no IP addresses, cookies or user details
        max_request_body_size="never",   # no request bodies (they hold phone numbers)
        include_local_variables=False,   # no variable values in stack frames

deploy/check.sh
#!/usr/bin/env bash
# deploy/check.sh, installed as /usr/local/sbin/user-notices-check.
# The four server checks for User Notices, run every 5 minutes by user-notices-check.timer.
# One email per problem: when it starts, again every 24 hours while it lasts, and when it clears.
set -uo pipefail

# Settings. Each can be overridden from the environment, for a test or another application.
MAIL_TO=${MAIL_TO:-"developer-a@example.internal, developer-b@example.internal"}
MAIL_FROM=${MAIL_FROM:-"user-notices-check@example.internal"}
SENDMAIL=${SENDMAIL:-/usr/sbin/sendmail}
STATE=${STATE_DIRECTORY:-/var/lib/user-notices-check}
DISK_PATHS=${DISK_PATHS:-"/ /var/lib/postgresql /var/backups/user-notices"}
DISK_LIMIT=${DISK_LIMIT:-80}                 # percent full
QUEUE_LIMIT=${QUEUE_LIMIT:-10000}            # jobs waiting in the Celery queue
QUEUE_READINGS=${QUEUE_READINGS:-4}          # 4 readings 5 minutes apart = above the limit for 15 minutes
ENV_FILE=${ENV_FILE:-/etc/user-notices/backend.env}
BACKUP_DUE=${BACKUP_DUE:-0300}               # last night's dump must be on the backup server by 03:00
BACKUP_LIST_CMD=${BACKUP_LIST_CMD:-"ssh -i /root/.ssh/backup_list_ed25519 -o BatchMode=yes -o ConnectTimeout=10 listing@backup.example.internal"}
CERT=${CERT:-/etc/ssl/notices.crt}
CERT_DAYS=${CERT_DAYS:-30}
HEARTBEAT_URL=${HEARTBEAT_URL:-}             # GlitchTip heartbeat monitor; empty = not used

HOST=$(hostname)
NOW=${CHECK_TIME:-$(date +%H%M)}
TODAY=${CHECK_DATE:-$(date +%Y%m%d)}
mkdir -p "$STATE"

send_mail() {   # send_mail <subject> <body>
  printf 'To: %s\nFrom: %s\nSubject: [user-notices %s] %s\n\n%s\n' \
    "$MAIL_TO" "$MAIL_FROM" "$HOST" "$1" "$2" | "$SENDMAIL" -t
}

problem() {     # problem <key> <subject> <details>
  local flag="$STATE/$1.alert"
  echo "PROBLEM $1: $2"
  if [[ ! -e $flag || -n $(find "$flag" -mmin +1440) ]]; then
    send_mail "PROBLEM: $2" "$3" && touch "$flag"
  fi
}

cleared() {     # cleared <key> <subject>
  local flag="$STATE/$1.alert"
  echo "ok $1"
  if [[ -e $flag ]]; then
    send_mail "CLEARED: $2" "The check passed at $(date '+%F %H:%M')." && rm -f "$flag"
  fi
}

# 1. Disk use, once per file system
declare -A seen
for path in $DISK_PATHS; do
  [[ -e $path ]] || continue
  read -r pct mount < <(df --output=pcent,target "$path" | tail -n 1)
  pct=${pct%\%}
  [[ -n ${seen[$mount]:-} ]] && continue
  seen[$mount]=1
  key="disk$(echo "$mount" | tr / _)"
  if (( pct > DISK_LIMIT )); then
    problem "$key" "disk $mount is ${pct}% full" \
      "$mount on $HOST is ${pct}% full; the limit is ${DISK_LIMIT}%. Largest folders: du -xh --max-depth=2 $mount | sort -h | tail"
  else
    cleared "$key" "disk $mount below ${DISK_LIMIT}%"
  fi
done

# 2. Jobs waiting in the Redis queue. REDIS_URL looks like redis://:PASSWORD@127.0.0.1:6379/0
redis_url=$(sed -n 's/^REDIS_URL=//p' "$ENV_FILE" | tr -d '"')
rest=${redis_url#redis://}
pass=${rest%@*}; pass=${pass#*:}
hostport=${rest##*@}; hostport=${hostport%/*}
db=${rest##*/}
if jobs=$(REDISCLI_AUTH="$pass" redis-cli -h "${hostport%:*}" -p "${hostport##*:}" -n "$db" LLEN celery 2>&1) \
   && [[ $jobs =~ ^[0-9]+$ ]]; then
  readings=$(cat "$STATE/queue.readings" 2>/dev/null || echo 0)
  if (( jobs > QUEUE_LIMIT )); then readings=$((readings + 1)); else readings=0; fi
  echo "$readings" > "$STATE/queue.readings"
  cleared redis "Redis answering again"
  if (( readings >= QUEUE_READINGS )); then
    problem queue "$jobs jobs in the Redis queue" \
      "More than $QUEUE_LIMIT jobs have waited for $(( (readings - 1) * 5 )) minutes. Check the workers: systemctl status user-notices-worker"
  elif (( readings > 0 )); then
    echo "watch queue: $jobs jobs, reading $readings of $QUEUE_READINGS above $QUEUE_LIMIT"
  else
    cleared queue "Redis queue below $QUEUE_LIMIT jobs ($jobs now)"
  fi
else
  problem redis "Redis did not answer" "redis-cli LLEN celery returned: $jobs"
fi

# 3. Last night's dump on the backup server, checked from 03:00
if [[ $NOW > $BACKUP_DUE || $NOW == "$BACKUP_DUE" ]]; then
  if listing=$($BACKUP_LIST_CMD 2>&1) && grep -q "usernotices-$TODAY-" <<<"$listing"; then
    cleared backup "backup for $TODAY on the backup server"
  else
    problem backup "no backup for $TODAY on the backup server" \
      "No file named usernotices-$TODAY-* was listed by: $BACKUP_LIST_CMD. Output: ${listing:0:500}"
  fi
fi

# 4. TLS certificate expiry
if openssl x509 -in "$CERT" -noout -checkend $((CERT_DAYS * 86400)) >/dev/null; then
  cleared cert "certificate valid for more than $CERT_DAYS days"
else
  problem cert "certificate expires within $CERT_DAYS days" \
    "$CERT on $HOST: $(openssl x509 -in "$CERT" -noout -enddate 2>&1). Rotation: RUNBOOK.md, TLS certificate."
fi

# Tell GlitchTip the check ran, so a stopped timer is noticed too
if [[ -n $HEARTBEAT_URL ]]; then curl -fsS -m 10 -o /dev/null "$HEARTBEAT_URL" || echo "heartbeat failed"; fi
exit 0

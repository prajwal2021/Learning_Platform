Use Python unless the application extends organization systems built on .NET, in which case use .NET. Node.js supports the same LLM APIs and is the alternative to record when the team already maintains Node.js services.

Why Python is the default

  • Most libraries for AI work and LLM API calls are Python libraries, so a feature added later, such as a chatbot, needs no second language.
  • Python projects run in a virtual environment, which keeps the project's packages apart from the system's. Stage 3 pins the version and Stage 4 creates the lock file (the file that pins every package version).
  • The choice narrows 2.6: a Python backend points to a Python API framework, FastAPI.

Basics API styles

An API style is the set of rules for how a client asks for something and how the answer comes back: what a request looks like, where it is sent, what format the answer uses, and whether the server can send data without a request.

  • Request and response. The client sends a request and waits for one answer. REST, GraphQL, gRPC and SOAP work this way.
  • Push. The server sends data when it has something new, over a connection the client keeps open. Server-Sent Events and WebSockets work this way.
  • Callback. Another system calls a URL in your application when an event happens on its side. Webhooks work this way.
  • Contract. A machine-readable description of the API that tools use to generate documentation, clients and tests: OpenAPI for REST, a schema for GraphQL, .proto files for gRPC, and WSDL for SOAP.

REST. Each resource has a URL, and HTTP methods act on it: GET /v1/users lists users, GET /v1/users/42 reads one, PATCH /v1/users/42 changes it. Request and response bodies are JSON, sent over HTTPS. The /v1 prefix is the API version, settled in Stage 3. FastAPI writes the OpenAPI contract and shows it at /docs (2.6). The full route list is written in Stage 6.

Default. Start with REST. Add another style for one part of the application when a requirement calls for it, and keep REST for the rest. One application can serve REST to its screens, stream one page with SSE, and receive webhooks from a provider.

Questions to ask, in order (the picker above walks through them):

  1. Is the caller a browser, a script or another team's system? Use REST.
  2. Must the server send updates without being asked? If only the server sends, use SSE. If both sides send often, use WebSockets.
  3. Does another system need to tell you when something happens on its side? Receive its webhooks, if that system can reach your application's network; otherwise ask its API on a schedule.
  4. Do several kinds of client need different shapes of the same data, and are REST endpoints multiplying for each screen? Consider GraphQL, with depth and cost limits.
  5. Are two internal services exchanging a high volume of calls, or streaming? Consider gRPC.
  6. Does an existing system you must call offer only SOAP? Use a SOAP client for that one integration.

Code for the styles User Notices could use

User Notices uses REST in its first release. The polling, SSE and webhook samples show what each style adds if a later requirement calls for it. The Python samples use current_user from app/auth/ and the settings object from app/settings.py (2.7).

REST, first release. The Users list screen's endpoint:

app/routers/users.py
# app/routers/users.py: the Users list screen's endpoint, GET /v1/users
from fastapi import APIRouter, Depends, Query

from app.auth import current_user
from app.interfaces.users import UserService, UserSummary
from app.services.users import get_user_service

router = APIRouter(prefix="/users")
MAX_PAGE_SIZE = 100


@router.get("", dependencies=[Depends(current_user)])
async def list_users(
    group: int | None = None,
    limit: int = Query(50, ge=1, le=MAX_PAGE_SIZE),
    offset: int = Query(0, ge=0),
    users: UserService = Depends(get_user_service),
) -> list[UserSummary]:
    # GET /v1/users?group=3&limit=50&offset=0 returns one page of users as JSON
    return await users.list_users(group_id=group, limit=limit, offset=offset)

main.py includes this router with the /v1 prefix (Stage 4), and get_user_service supplies the UserService through dependency injection (FastAPI builds the object a function names in its parameters and passes it in; Stage 4). With the session cookie (the cookie named session that POST /v1/auth/login sets), GET /v1/users?group=3&limit=50 returns a JSON list of UserSummary rows. A limit above 100 is refused with HTTP 422 (the parameter failed validation), and a request without the cookie with HTTP 401 (not signed in). FastAPI lists the endpoint and its three parameters at /docs.

Polling, no new server code. Notice history reloads the list while a notice is sending:

Notice history page
// Notice history page: reload the list every 5 seconds while a notice is sending.
// apiBase is "" in production, where the reverse proxy sends /v1 to the backend,
// and the backend's local address during development (Stage 6).
async function refreshWhileSending(render, apiBase = "", everyMs = 5000) {
  for (;;) {
    const res = await fetch(`${apiBase}/v1/notices`, { credentials: "include" });
    if (!res.ok) throw new Error(`GET /v1/notices returned ${res.status}`);
    const notices = await res.json();
    render(notices);
    if (!notices.some((n) => n.status === "sending")) return;
    await new Promise((resolve) => setTimeout(resolve, everyMs));
  }
}

GET /v1/notices is the route the page already calls. A status change shows up to 5 seconds late, and each open page keeps sending requests until no notice is sending.

Server-Sent Events, if Notice history must show a send as it happens. The endpoint, added to the notices router:

app/routers/notices.py
# Added to app/routers/notices.py, which already has router = APIRouter(prefix="/notices"),
# only if Notice history must show a send progressing without a reload.
import asyncio
from collections.abc import AsyncIterable

from fastapi import Depends
from fastapi.sse import EventSourceResponse, ServerSentEvent

from app.auth import current_user
from app.db.progress import read_progress  # the notice's status and message counts


@router.get(
    "/{notice_id}/progress",
    response_class=EventSourceResponse,
    dependencies=[Depends(current_user)],
)
async def notice_progress(notice_id: int) -> AsyncIterable[ServerSentEvent]:
    last = None
    while True:
        progress = await read_progress(notice_id)
        # for example {"status": "sending", "sent": 1200, "failed": 3, "total": 5000}
        if progress != last:
            yield ServerSentEvent(data=progress, event="progress")
            last = progress
        if progress["status"] in ("sent", "failed"):
            return
        await asyncio.sleep(1)

The page reads the stream with the browser's EventSource:

Notice history page
// Notice history page: show one send's progress as the server reports it.
function watchProgress(noticeId, render, apiBase = "") {
  const source = new EventSource(`${apiBase}/v1/notices/${noticeId}/progress`, {
    withCredentials: true, // sends the session cookie when apiBase is another origin
  });
  source.addEventListener("progress", (event) => {
    const progress = JSON.parse(event.data);
    render(progress);
    if (progress.status === "sent" || progress.status === "failed") source.close();
  });
  return source; // call source.close() if the page is left before the send ends
}

  • In the output, the server line names uvicorn, the program that runs the FastAPI application. The -N flag stops curl from buffering, so each event prints as it arrives.
  • fastapi.sse needs FastAPI 0.135.0 or later (Source 20). Stage 3 pins the version.
  • FastAPI sends a keep-alive comment every 15 seconds when there is nothing new, and sets Cache-Control: no-cache and X-Accel-Buffering: no, which stops nginx (the reverse proxy) from holding events back (Source 20).
  • read_progress is a new data layer function that reads the notice's status and its message counts.
  • Each open page holds one connection. Without HTTP/2, a browser allows 6 per domain, shared by all its tabs (Source 21).
  • When a stream ends, the browser reconnects on its own (Source 19). The page calls close() on the last event, so it does not.

Webhooks, only if the network team opens a path from the provider. The receiver checks the signature, drops repeated event ids and hands the work to the task queue (Celery, which runs jobs in a separate worker process; Stage 8):

app/routers/sms_webhooks.py
# app/routers/sms_webhooks.py: only if the network team opens a path from the provider
import base64
import hashlib
import hmac
import time

from fastapi import APIRouter, HTTPException, Request, Response
from fastapi.concurrency import run_in_threadpool
from redis.asyncio import Redis

from app.settings import settings
from app.worker.tasks import apply_delivery_report  # Celery task (Stage 8)

router = APIRouter(prefix="/webhooks")
redis = Redis.from_url(settings.redis_url)
TOLERANCE_SECONDS = 300  # reject deliveries signed more than 5 minutes ago or ahead


def signature_ok(msg_id: str, timestamp: str, body: bytes, header: str) -> bool:
    key = base64.b64decode(settings.sms_webhook_secret.removeprefix("whsec_"))
    signed = f"{msg_id}.{timestamp}.".encode() + body
    expected = base64.b64encode(hmac.new(key, signed, hashlib.sha256).digest())
    return any(
        hmac.compare_digest(expected, sig[3:].encode())
        for sig in header.split()
        if sig.startswith("v1,")
    )


@router.post("/sms-delivery", status_code=204)
async def sms_delivery(request: Request) -> Response:
    msg_id = request.headers.get("webhook-id", "")
    timestamp = request.headers.get("webhook-timestamp", "")
    body = await request.body()
    if not msg_id or not timestamp.isdigit() or abs(time.time() - int(timestamp)) > TOLERANCE_SECONDS:
        raise HTTPException(400, "Missing or expired webhook headers")
    if not signature_ok(msg_id, timestamp, body, request.headers.get("webhook-signature", "")):
        raise HTTPException(401, "Signature does not match")

    seen_key = f"webhook:sms:{msg_id}"  # the same webhook-id on every retry
    if not await redis.set(seen_key, "1", nx=True, ex=7 * 24 * 3600):
        return Response(status_code=204)  # a repeated delivery: already queued
    try:
        # .delay() is a blocking call to the broker, so it runs in the threadpool
        await run_in_threadpool(apply_delivery_report.delay, body.decode())
    except Exception:
        await redis.delete(seen_key)  # let the provider's retry queue it
        raise
    return Response(status_code=204)
  • The headers, the signed content (webhook-id, timestamp and body joined by full stops), the whsec_ secret format and the 2xx answer follow the Standard Webhooks specification (Source 22). Check which scheme the provider uses.
  • The webhook-id stays the same on every retry, so it is the key for dropping repeats. Keep the key longer than the provider's retry schedule; 7 days here.
  • Celery's .delay() sends the job to the broker (the message store that holds the queue; Redis, from Stage 8) over the network, a blocking call, so it runs through run_in_threadpool (2.6 explains the threadpool).
  • If the job cannot be queued, the key is removed and the request fails, so the provider's next retry is queued.
  • redis_url comes from REDIS_URL, which Stage 8 adds. The webhook secret is a new setting, SMS_WEBHOOK_SECRET in this sample, added to .env.example in the same pull request (the reviewed change that adds the code; Stage 4). The guide's settings list does not include it, because the first release has no webhook.

gRPC. The .proto file is the contract. protoc generates the client and server code from it, and WatchStatus is a server-streaming call (Source 11):

delivery.proto
// Illustration outside User Notices: a contract between two internal services
syntax = "proto3";

package delivery.v1;

service DeliveryStatus {
  // One request, one response
  rpc GetStatus (StatusRequest) returns (StatusReply);
  // The server streams each status change as it happens
  rpc WatchStatus (WatchRequest) returns (stream StatusReply);
}

message StatusRequest {
  string message_id = 1;
}

message WatchRequest {
  repeated string message_ids = 1;
}

message StatusReply {
  string message_id = 1;
  string status = 2;
  int64 updated_unix = 3;
}

2.6API framework

With a Python backend, use FastAPI to serve the API style chosen in 2.5. FastAPI describes the API in an OpenAPI document and shows it at /docs. Write each endpoint as async def when every slow call in it supports await, and as plain def when one does not.

QuestionWhich framework serves the API, and does each library it uses for network or database calls support await?

async def or plain def

A network or database call spends most of its time waiting for the other side. An async def endpoint that awaits such a call lets the server handle other requests during the wait. The original walkthrough compared it to cooking: start the water heating, then heat the pan while the water heats, instead of waiting for the water before touching the pan.

The one combination to avoid is async def around a blocking call. The call holds the whole server process until it returns, so every other request waits too.

main.py
import httpx
import requests  # blocking library: no await support
from fastapi import FastAPI

from app.settings import settings

app = FastAPI()
client = httpx.AsyncClient()

# Correct: async def, and the call supports await
@app.get("/v1/provider-status")
async def provider_status():
    r = await client.get(f"{settings.sms_api_url}/status")
    return {"ok": r.status_code == 200}

# Correct: plain def, because requests cannot be awaited
@app.get("/v1/provider-status-sync")
def provider_status_sync():
    r = requests.get(f"{settings.sms_api_url}/status")
    return {"ok": r.status_code == 200}

# Wrong: a blocking call inside async def stops the server while it waits
@app.get("/v1/provider-status-wrong")
async def provider_status_wrong():
    r = requests.get(f"{settings.sms_api_url}/status")
    return {"ok": r.status_code == 200}

settings.sms_api_url holds the provider's address, read from SMS_API_URL (2.7). The /status path is a placeholder; a real provider's paths come from its documentation.

Rate limits are not a reason to use plain def

Plain def endpoints run at the same time as each other, up to the threadpool's 40 threads, so they do not make calls go out one at a time. When a provider limits requests per second, limit the calls on your side.

from aiolimiter import AsyncLimiter

from app.settings import settings

# At most 10 calls per 1 second (use the provider's published limit)
sms_limiter = AsyncLimiter(10, 1)

async def send_one(client, payload):
    async with sms_limiter:
        return await client.post(f"{settings.sms_api_url}/messages", json=payload)

For bulk sends, Stage 8 moves the work to a task queue and uses the queue's rate limit setting instead. A limiter library chosen here is pinned in Stage 3 like any other dependency.

Common mistakes

Each one shows how you notice it and how to fix it. The first six are the guide's; the rest come up when the steps above are skipped.

Choosing a tool because it is new or familiar, without a reason tied to a requirement

How you notice it. The reason column describes the tool, not a Stage 1 fact.

Fix. Rewrite the reason from the 2.1 inputs. If no input supports the tool, choose again.

Using plain def to slow calls to a rate-limited server

How you notice it. The provider returns HTTP 429, Too Many Requests, under load.

Fix. A client-side limiter now, or the task queue's rate limit in Stage 8.

Missing a Stage 1 constraint, such as a mandated database

How you notice it. The database team or the deployment review raises it.

Fix. Run the 2.8 check against every constraint before Stage 3.

Choosing GraphQL or gRPC for an application with one front end whose screens list and edit records

How you notice it. A schema or .proto files, and generated code, to maintain for screens that each read or change one kind of record.

Fix. REST covers it with less code. Keep GraphQL or gRPC for the callers that need them (2.5).

Asking the server for updates every second when Server-Sent Events can send them as they happen

How you notice it. Every open page sends a request each second, and most answers hold nothing new.

Fix. SSE for that page, or polling every few seconds when a delay is acceptable.

Accepting webhooks without checking the signature, or processing the same event twice

How you notice it. Anyone who finds the URL can send an event, and a retried delivery is counted twice.

Fix. Check the signature and timestamp, drop repeated event ids, answer quickly and do the work in a queue (the Webhooks code in 2.5).

Calling a blocking library inside async def

How you notice it. Every page slows down while one slow call waits.

Fix. Use the library's async client, or declare the endpoint with def.

Forgetting that Next.js runs on Node.js

How you notice it. Stage 3's version table has no Node.js row.

Fix. Add Node.js to the record under the front end.

Storing files in database tables

How you notice it. Database size and backup time grow with every upload.

Fix. Object storage, with the file's key in a table (Stage 7).

Writing a key or password into the code

How you notice it. A secret appears in a committed file.

Fix. List it in 2.7 so Stage 4 puts it in .env. If it was committed, remove it and change the key.

Leaving the file storage row empty

How you notice it. Nobody can tell whether files were considered.

Fix. Write "None" and the reason.

Self-check from the guide

The guide's four questions for Stage 2. Open each one to see its answer.

An endpoint uses a payment library that has no await support. How do you declare the endpoint, and what does FastAPI do with it?

With plain def. FastAPI runs it in a threadpool, so the blocking call does not stop the server from handling other requests.

The SMS provider accepts a limited number of requests per second. A teammate suggests plain def so the calls go out one at a time. What is wrong with that?

Plain def functions also run concurrently in the threadpool, so the calls do not go out one at a time. Limit the rate with a client-side limiter, or with the task queue's rate limit setting.

Your organization already licenses MSSQL and its database team supports it. Which database do you choose, and which stage's output tells you?

MSSQL. The Stage 1 constraints record it, and a held license with organizational support overrides the PostgreSQL default.

Notice history must show a 5,000-message send progressing without a reload. Which API style do you add for that page, and why not WebSockets?

Server-Sent Events. Only the server sends the progress, and SSE is plain HTTP with automatic reconnection. WebSockets carry messages in both directions, which this page does not need, and the proxy has to pass their upgrade headers.

What Stage 1 produces

Stage 1 produces a requirements document in seven parts, and each part is the input to at least one later stage. Select a part to see which stages read it and what they do with it.

Process

The Stage 1 process

Stage 1 runs in six steps, from the first request to a requirements document the requester has agreed. Steps 3 to 5 repeat until the read-back finds nothing missing.

1Record the request

Write the request as it was given, who asked, and the problem it solves.

You finish with: the request in the requester's own words

2Find the people

The users, the data owner, and whoever runs the servers.

You finish with: a People table with names and roles

3Walk through the work

Ask each kind of user to show a task from start to finish, step by step.

You finish with: notes of every step, value and system they mention

4Draft the seven parts

Screens, data, services, load, constraints, target, operating requirements.

Unknowns go in as open questions, each with who can answer it

5Read it back

Walk the requester and users through the draft, screen by screen. Ask what is missing or wrong.

Gaps found go back to step 3

6Agree and record

The requester agrees the document. Give it a version number and a date.

Stage 2 starts from this version. Later changes go in the change log

gaps found

Questions for step 3

Ask each kind of user separately. Staff who send notices and the administrator who creates staff accounts use different screens.

  • Show me how you do this today, from the start.
  • What happens next? What do you do after that?
  • What do you look at before you decide?
  • What goes wrong, and what do you do then?
  • How often do you do this, and when is it busiest?
  • Who else needs to see or approve it?
  • What should the application never do?

Ask to see the tools in use today: spreadsheets, emails, paper forms. Each column or form field is a candidate item for Part 2, Stored data.

Part 1 of 7

Screens

List every screen a user sees, and for each one write what the user does on it, the data it shows or accepts, and whether it is needed at launch. Stage 6 turns each screen into a page, a route (the address the page is served at) and an API call.

How to find the screens

  1. Follow a task. Take a task from your step 3 notes, from start to end. Each place the user looks at or types into is a candidate screen.
  2. Follow the verbs. List, open, create, edit, delete, search, send, approve, export. Each verb is a screen or an action on one.
  3. Check every thing in Part 2. Each thing the application stores can be created, viewed, changed and removed on some screen, or you record why it cannot.
  4. Add the edges. Sign in, forgotten password, a list with nothing in it, a user without permission.
  5. Mark the timing. Needed at launch, or Later.

Screen or action. A screen shows its own information or has its own form. An action is a button or control on a screen.

Part 2 of 7

Stored data

List every piece of information the application stores, reads or logs, grouped by the thing it describes. Stage 7 turns this list into fields and tables, so you do not design tables here.

How to build the list

  1. Read it off the screens. For each screen in Part 1, write what it shows and what the user types or picks on it.
  2. Group by thing. Put each value under the thing it describes: a user, a group, a notice. Each thing usually becomes a table in Stage 7.
  3. Ask the life questions. For each thing: who creates it, who changes it, can it be deleted, and how long it is kept. The period goes into Part 7 as its retention period.
  4. Ask what must be logged and audited. Every message sent, every sign-in, and each action that needs an audit record of who did what, to which record and when. Logs and audit records are stored data and need tables; Stage 7 builds the audit table. Part 7 lists which actions are audited.
  5. Mark sensitive data. Personal data such as phone numbers, and passwords, which are never stored as typed. Sensitive data also goes into Part 5, Constraints.
  6. Count the records. How many exist today, and how many are added per day or per month. This is data volume, which is separate from load in Part 4.
  7. Note any files. Images, PDFs or uploads. Stage 2 sends files to object storage (a service that stores whole files by name, separate from the database), not the database.

External services

List every system outside the application that it calls or that calls it, with what is sent, how often, and the limits that system sets. Stage 2 chooses the API approach from this list, and Stage 8 sets the outbound rate from the limits.

Part 4 of 7

Load

Record load as two numbers, registered users and concurrent requests, and list every burst. Stage 8 tests the application at the concurrent number, not the registered one.

The two numbers

NumberWhat it countsUser Notices
Registered usersAccounts that can sign in150 staff accounts
Concurrent requestsRequests the backend is handling at the same moment, at the busiest timeAt most 40

Records the application stores are not users. User Notices holds 60,000 user records, but those people receive text messages and never sign in. They add data, not load.

Estimating concurrent requests

When nobody can give you the number, estimate it and record that it is an estimate.

concurrent requests = (users online at the peak × requests per user per minute ÷ 60) × seconds per request

Bursts

A burst is a known event that sends many requests or jobs at once, even when daily traffic is light. For each one, record what happens, when, and how many.

Ask about scheduled bulk sends, nightly jobs, month end, the start of a term or a shift, deadlines, and announcements that send everyone to the application at once.

Part 7 of 7

Operating requirements

Write down the requirements for running the application after launch: which actions are audited, how long each kind of record and log is kept, how much recent data may be lost, how long the application may be down while it is restored, and when an update may interrupt users. Stage 7 builds the audit table, Stage 9 chooses the backups and the deployment strategy from these answers, and Stage 10 sets the retention, the restore tests and the update windows.

Basics: Logs, audit records and recovery

Application log
The lines the application writes while it runs, such as each request, each error and each background job, with the time. Developers read it to find out what happened, and it is kept for a short period.
Audit record
A stored record of who did what, to which record and when, such as a staff member changing a user's opt-in. Audit records go in their own table, which the application can add to but not change.
Retention period
How long a kind of record or log is kept before it is deleted. The organization's records policy often sets it.
Recovery point
How much recent data may be lost if the database server fails. Write it as the backup a restore would start from, such as the previous night's backup, or as a length of time. With a recovery point of the previous night's backup, a restore brings back everything up to that backup, and the changes made after it are lost. A length of time has to allow for the copy off the server: a backup still on the failed server is lost with it.
Recovery time
How long the application may be down while it is restored after a failure.
Update window
When an update may interrupt the application, and for how long.

      Practice

      The diary application

      Work through Stage 1 for a diary application on your own, then compare each part with the model answer. What you type stays in this browser.

      The request as received

      We want a simple online diary for our members. Each member signs in, writes entries, edits or deletes old ones, and searches their own entries for a word.

      What the requester says when asked

      Use these answers as if you had asked the questions in an interview.

      • There are 2,000 members today, and 5,000 are expected in a year.
      • Most entries are written in the evening. At the busiest time, up to 300 members are online at once.
      • A member who is online makes about two requests a minute: opening, saving and searching entries. Assume each request takes about 0.5 seconds.
      • Entries are private. Only the member who wrote an entry can read it.
      • Entries are kept until the member deletes them. Closing an account deletes all of its entries.
      • A forgotten password is reset through a link sent by email.
      • The data may be stored with a cloud provider, in the same country as the organization.
      • Every sign-in, successful or failed, must be recorded with the member and the time. Sign-in records are kept 1 year, and application logs 30 days.
      • If the server fails, losing up to one day of entries is acceptable, and the diary must be back within 8 hours.
      • Updates may run at night, between 1:00 and 5:00, and may interrupt the diary for up to 10 minutes.

      Worksheet

      Part 1Screens

      What does a member do, from signing in to signing out? Which screen opens one entry? Where do search results appear?

      Model answer

      Sign in; Forgotten password; Entry list, newest first; Entry, to write, view, edit and delete; Search results; Account, to close the account.

      Part 2Stored data

      What does one entry hold? Who may read it? What happens to entries when a member leaves?

      Model answer

      Members (email, password stored as a hash); entries (author, text, date, time last changed); sign-in audit records (member, time, successful or failed). Entries are kept until deleted, and closing an account deletes them. Counts: 2,000 members today, 5,000 in a year.

      Part 3External services

      How does a member who has forgotten their password get back in?

      Model answer

      An email service, to send password reset links: one email per reset request. The account owner and the service's limits are open questions.

      Part 4Load

      How many members, and how many requests at the same moment? Is there a time of day when many members write at once?

      Model answer

      2,000 registered members, 5,000 expected in a year. At the evening peak: 300 online × 2 requests a minute ÷ 60 × 0.5 seconds = 5 concurrent requests, estimated. If the number online grows with membership, about 750 online and 13 concurrent requests in a year. No scheduled bursts.

      Part 5Constraints

      Who may see an entry? Where may entries be stored?

      Model answer

      Entries are private to their author. Data may be stored with a cloud provider in the same country.

      Part 6Deployment target

      A cloud provider or the organization's own servers? How many environments?

      Model answer

      A cloud provider in the same country, with a live environment and a sandbox. To confirm with the infrastructure contact.

      Part 7Operating requirements

      Which actions need an audit record? How long are logs and records kept? How much recent data may be lost, and how long may the diary be down? When may an update interrupt members?

      Model answer

      Audit: every sign-in, successful and failed, with the member and the time. Retention: application logs 30 days; sign-in records 1 year; entries until the member deletes them. Recovery: recovery point the previous night's backup, so up to one day of entries may be lost; recovery time 8 hours. Updates: at night, between 1:00 and 5:00, with up to 10 minutes of interruption.

      Open questions in the model answer

      How do members register? Which email service is used, and who owns the account? How many entries does a member write per day?

      At about 5 concurrent requests and no bursts, Stage 8 for this application is a load test and a decision table (the Stage 8 table that records, for each layer such as a cache or a queue, whether the measured load needs it) with most layers marked not needed. With a recovery point of the previous night's backup and updates allowed at night, Stage 9 can use a nightly backup copied off the server and stop the diary briefly for each update, and Stage 10 removes logs after 30 days and sign-in records after 1 year.

      Self-check

      1. An application will have 80,000 registered users. What second number do you need before Stage 8, and why?

        Show answer

        The number of concurrent requests, and how they arrive. Stage 8 decisions depend on how many requests arrive at the same moment, not on how many users are registered.

      2. A nightly job will send 10,000 reminder messages. Where does that belong in the requirements?

        Show answer

        Under load, as a burst of 10,000 messages each night, and under external services, as the message provider. If each message is logged, it is also stored data.

      3. Staff ask who changed a user's opt-in last week, and the application cannot say. Which requirement was missing, and which stages build what it needs?

        Show answer

        The audit requirement: which actions need a record of who did what, to which record and when. Stage 7 builds the audit table and the permissions that keep it from being changed, and Stage 10 keeps it for the retention period.

      4. A requester says about 2,000 people use the current system. Which load number is that, and what do you ask next?

        Show answer

        Registered users. Ask how many use the system at the busiest moment, when that moment is, and how the number is expected to grow. If nobody knows, estimate concurrent requests with the calculation in Part 4 and record that it is an estimate.

      5. The SMS provider accepts a limited number of requests per second. Which part of the requirements records that, and which stage uses it?

        Show answer

        Part 3, External services, in the Limits row. Stage 8 sets the worker concurrency below the limit.

      6. A requester asks for a dashboard. What do you ask to turn that into a screen requirement?

        Show answer

        Who uses it, which decision they make from it, which records or numbers it shows, how up to date they must be, and which screen it opens from.

      7. Nobody knows how long a kind of record must be kept. What do you write?

        Show answer

        An open question in Part 7: how long that kind of record is kept, with the data owner as the person who can answer and Stage 10 as the stage that needs the answer.

Overview

Stage 8 at a glance

Stage 8 is a loop. Test, find what failed first, make one change, and test again until the pass criteria hold; then choose the product for each layer added and record a decision for every layer.

The cheaper fix comes before any layer. Each pass round the loop changes one thing, so each test result can be traced to one change.

Part 1

Plan the test

Write the test plan before the first run: the load to test, what counts as passing, where the test runs, and which requests it sends. A test run without a written plan produces numbers nobody can compare.

Take these from the Stage 1 requirements.

1.2 Write the pass criteria

Fix the criteria before the first run, so a result cannot be reinterpreted afterwards.

  1. Errors. Zero at the working level. A 5xx response, a timeout and a refused connection all count.
  2. Response time. p95 under 1 second for every request type.
  3. Headroom. Working level at least 2 times the expected concurrency. For User Notices: at least 80.

1.3 Prepare the test environment

The SMS stub, as a FastAPI app on the load machine or a spare port:

# Stands in for the SMS provider during tests. Run with: uvicorn sms_stub:app --port 9000
import asyncio, itertools, time
from fastapi import FastAPI

app = FastAPI()
counter = itertools.count(1)
DELAY_SECONDS = 0.2   # set close to the provider's measured response time


@app.post("/messages")
async def send(payload: dict):
    await asyncio.sleep(DELAY_SECONDS)

Part 2

Run the load test and the stress test

Three runs, in this order: the load test at the expected concurrency, the stress test past it, and the bulk test. Run each against the sandbox and save the results with the commit they were run on.

2.1 Write the test script

One Locust user class covers all five scenarios. Each @task weight matches the share in 1.4.

import itertools, os, random
from locust import HttpUser, task, constant

ACCOUNTS = itertools.cycle([f"loadtest{n:02d}@example.org" for n in range(1, 51)])
PASSWORD = os.environ["LOADTEST_PASSWORD"]
GROUP_IDS = [1, 2, 3, 4]
USER_IDS = range(1, 60001)


class StaffMember(HttpUser):
    # No pause between requests: each simulated user always has one request
    # in flight, so 40 users hold about 40 concurrent requests.
    wait_time = constant(0)

    def on_start(self):
        # Each simulated user signs in once. The API answers 204 and sets the
        # session cookie, which the client sends with every later request.
        with self.client.post("/v1/auth/login", name="POST /v1/auth/login",
                              json={"email": next(ACCOUNTS), "password": PASSWORD},
                              catch_response=True) as response:
            if response.status_code != 204 or "session" not in self.client.cookies:
                response.failure(f"sign-in failed: {response.status_code}")

    @task(40)
    def users_list(self):
        self.client.get(f"/v1/users?group={random.choice(GROUP_IDS)}&limit=50&offset=0",
                        name="GET /v1/users?group=[id]")

    @task(25)
    def user_detail(self):
        self.client.get(f"/v1/users/{random.choice(USER_IDS)}", name="GET /v1/users/[id]")

    @task(20)
    def notice_history(self):
        self.client.get("/v1/notices", name="GET /v1/notices")

    @task(10)
    def edit_user(self):
        self.client.patch(f"/v1/users/{random.choice(USER_IDS)}",
                          json={"opted_in": True}, name="PATCH /v1/users/[id]")

    @task(5)
    def schedule_notice(self):
        # A send time in the future: the notice is stored and nothing is sent
        self.client.post("/v1/notices", json={"text": "Load test notice", "group_id": 1,
                                              "send_at": "2030-01-01T09:00:00Z"},
                         name="POST /v1/notices")

The name argument groups requests by route, so the results show one row per request type instead of one row per user id. The script edits users and creates notices, so run it only against the sandbox.

Real staff pause between clicks. A script with pauses (wait_time = between(2, 5), for example) needs more simulated users to reach the same concurrency. With no pause, the number of users equals the number of requests in flight, which matches how Stage 1 records load.

Part 4

Try the cheaper fixes first

Indexes, query changes and route changes need no new service, so they come before any layer. For User Notices, the load test showed no slow queries, so this part recorded no change.

4.1 Find the slow queries

Set log_min_duration_statement = 250 in postgresql.conf on the sandbox and reload PostgreSQL (SELECT pg_reload_conf(); or systemctl reload). Every statement that takes longer than 250 ms is then written to the log with its duration. Run the load test again and collect the statements that appear most often.

4.2 Read the query plan

Run each slow statement with EXPLAIN in front of it.

EXPLAIN (ANALYZE, BUFFERS)
SELECT id, name, phone FROM users
WHERE group_id = 3
ORDER BY name
LIMIT 50;
In the planMeaningResponse
Seq Scan on users, with a large Rows Removed by FilterThe whole table is read to return a few rowsIndex the filtered column
Index Scan or Bitmap Index Scan using the expected indexThe index is usedLook elsewhere: the sort, a join, or the amount of data returned
Sort with Sort Method: external mergeThe sort did not fit in memoryIndex the sort column together with the filter column, or return fewer rows

EXPLAIN ANALYZE runs the statement. For an UPDATE or DELETE, wrap it in BEGIN; and ROLLBACK; so nothing changes.

4.3 Remove indexes that nothing uses

Each index adds work to every insert and update. After a load test that covers all the scenarios, list the indexes with no scans:

SELECT relname AS table_name, indexrelname AS index_name, idx_scan
FROM pg_stat_user_indexes
WHERE idx_scan = 0;

Keep indexes that back a primary key or a unique constraint, even with zero scans. Confirm on the live database before dropping any other index, since the sandbox test may not cover every query.

4.4 Check the routes

  • Queries per request. Turn on SQL logging in the sandbox (echo=True on the engine) and call one list endpoint. One query for the list and one more for each row is the N+1 pattern. Load the related rows in the same query, with a join or SQLAlchemy's selectinload.
  • Page size. Every list endpoint returns a page, for example 50 rows, and never the whole table.
  • Response size. Return the fields the screen shows, not every column.
  • Load per route. The stats file lists request counts and p95 by route. A route with a high count and a high p95 is the first one to fix.

Part 5

Add a task queue

The bulk test in 2.5 is the measurement that calls for a queue in User Notices. After this part, Send now returns HTTP 202 in about 3 seconds, and one worker instance with 2 processes sends the 5,000 messages at a rate the SMS provider accepts.

Before, one request did all the work. After, the request claims the notice, creates one queued record per recipient, puts one send job per record on the broker and returns. The worker's 2 processes take the jobs; each claims its record, checks the opt-out and sends, 8 messages a second in all. Celery beat starts send_due_notices every minute, which does the same for scheduled notices that are due. The API and the worker both read and write PostgreSQL. The code in this part was run with Celery 5.6.3, Redis 8.2.2, PostgreSQL 18.6 and Python 3.14, against the SMS stub from 1.3; the results are in 5.8.

"""The Celery application, and the clients each worker process opens for itself."""
import httpx
from celery import Celery
from celery.signals import worker_process_init
from sqlalchemy import create_engine
from sqlalchemy.orm import Session
from app.services.sms import ProviderSmsClient
from app.settings import get_settings

settings = get_settings()

celery_app = Celery("user_notices", broker=settings.redis_url,
                    include=["app.tasks.notices"])
celery_app.conf.update(
    task_acks_late=True,           # acknowledge after the task returns (5.4)
    worker_prefetch_multiplier=1,  # each process reserves one job at a time
    task_ignore_result=True,       # outcomes are recorded in notice_messages
    broker_connection_retry_on_startup=True,
    beat_schedule={
        "send-due-notices": {
            "task": "app.tasks.notices.send_due_notices",
            "schedule": 60.0,      # every minute
        },
    },
)

_engine = None  # set in each worker process by open_clients
_sms = None


@worker_process_init.connect
def open_clients(**kwargs):
    """Runs in each worker process after Celery starts it. The database pool and the
    HTTP client belong to that process; nothing is shared with the parent process."""
    global _engine, _sms
    _engine = create_engine(settings.database_url)
    _sms = ProviderSmsClient(httpx.Client(
        base_url=settings.sms_api_url,
        headers={"Authorization": f"Bearer {settings.sms_api_key}"},
        timeout=httpx.Timeout(10.0, connect=5.0)))


def db() -> Session:
    return Session(_engine)


def sms() -> ProviderSmsClient:
    return _sms

Celery starts the 2 processes by forking the instance's main process. A database pool or HTTP client opened before the fork would have its connections shared by both processes, so open_clients opens them once per worker process when it starts, in Celery's worker_process_init hook (Source 6). The same postgresql+psycopg:// DATABASE_URL works for the synchronous engine. The tasks call worker.db() and worker.sms() to use them. Measured with --concurrency 2 after a send, with no job running: pg_stat_activity showed 2 idle connections from usernotices_app_a, one per process, and none from the main process. The engine connects on first use, so before the first job the processes hold none. When PgBouncer is running (7.5), its own server connections appear under the same role, 20 at most with the settings there, so subtract them.

5.3 Write the tasks

Celery tasks are plain functions, so in Stage 8 the SmsClient interface becomes synchronous: send is a plain def, and the provider client uses httpx.Client. Only the worker calls the provider from now on.

# app/interfaces/sms.py (Stage 8: send is a plain function, called by the workers)
from typing import Protocol


class SmsError(Exception):
    """The provider did not accept a message."""


class SmsClient(Protocol):
    def send(self, phone: str, text: str) -> str: ...  # the provider's message id; raises SmsError
# app/services/sms.py
"""The SMS provider client. It implements SmsClient from app/interfaces/sms.py
with httpx.Client. app/worker.py creates one in each worker process."""
import httpx
from app.interfaces.sms import SmsError


class ProviderSmsClient:
    def __init__(self, http: httpx.Client):
        self.http = http  # base URL, API key header and timeouts are set in app/worker.py

    def send(self, phone: str, text: str) -> str:
        response = self.http.post("/messages", json={"to": phone, "text": text})
        if response.status_code >= 400:  # the provider did not accept the message
            raise SmsError(f"provider answered {response.status_code}")
        return response.json()["id"]

The SQL that both the API and the worker run goes in one module, so the two cannot drift apart:

# app/db/sending.py
"""SQL for sending a notice. The API's send_notice runs the first two with its async
session; the tasks in app/tasks/notices.py run all three with the worker's session."""
from sqlalchemy import text

# Claims a scheduled notice. No row comes back if Send now or the scheduler claimed it first.
CLAIM_NOTICE = text(
    "UPDATE notices SET status = 'sending' "
    "WHERE id = :id AND status = 'scheduled' RETURNING id")

# One queued record per opted-in user in the notice's group; returns the new record ids.
QUEUE_MESSAGES = text(
    "INSERT INTO notice_messages (notice_id, user_id, status) "
    "SELECT n.id, u.id, 'queued' FROM notices n "
    "JOIN users u ON u.group_id = n.group_id AND u.opted_in "
    "WHERE n.id = :id "
    "ON CONFLICT (notice_id, user_id) DO NOTHING RETURNING id")

# Closes a notice once none of its records is queued or sending:
# 'sent' if at least one message was sent, otherwise 'failed'.

synchronous engine and SMS client that app/worker.py opens in each worker process."""
import logging
import httpx
from sqlalchemy import text
from app import worker

from app.worker import celery_app

log = logging.getLogger(__name__)
MAX_ATTEMPTS = 3  # tries when the provider cannot be reached


def queue_jobs(message_ids: list[int]) -> None:
    """Put one send_message job per queued record on the queue."""
    for message_id in message_ids:
        send_message.delay(message_id)


@celery_app.task
def send_due_notices() -> None:
    """Started by Celery beat every minute. Finds due notices with the
    (status, send_at) index and claims each one before queuing its jobs."""
    with worker.db() as db:
        due = db.scalars(text(
            "SELECT id FROM notices WHERE status = 'scheduled' AND send_at <= now() "
            "ORDER BY send_at")).all()
    for notice_id in due:
        with worker.db() as db, db.begin():
            if db.scalar(CLAIM_NOTICE, {"id": notice_id}) is None:
                continue  # claimed first by Send now or by another run
            message_ids = db.scalars(QUEUE_MESSAGES, {"id": notice_id}).all()
        queue_jobs(message_ids)  # after the commit, so the workers can see the records
        log.info("notice %s: %s messages queued", notice_id, len(message_ids))


@celery_app.task(rate_limit="8/s")  # per worker instance; its 2 processes share it
def send_message(message_id: int, attempt: int = 1) -> None:
    with worker.db() as db:
        # Claim the record. If another delivery of this job has it, no row comes back.
        claimed = db.scalar(text(
            "UPDATE notice_messages SET status = 'sending' "
            "WHERE id = :id AND status = 'queued' RETURNING id"), {"id": message_id})
        db.commit()
        if claimed is None:
            return

        # Read the opt-out just before the call: it can change during a send.
        row = db.execute(text(
            "SELECT m.notice_id, u.phone, u.opted_in, n.text FROM notice_messages m "
            "JOIN users u ON u.id = m.user_id JOIN notices n ON n.id = m.notice_id "
            "WHERE m.id = :id"), {"id": message_id}).one()
        db.commit()  # no transaction stays open during the call to the provider
        if not row.opted_in:
            record(db, message_id, row.notice_id, "failed")  # opted out: nothing sent
            log.info("message %s: user opted out, not sent", message_id)
            return

        try:
            provider_id = worker.sms().send(row.phone, row.text)
        except SmsError as exc:
            record(db, message_id, row.notice_id, "failed")
            log.warning("message %s: %s", message_id, exc)
            return
        except (httpx.ConnectError, httpx.ConnectTimeout):
            # The request never reached the provider, so it is safe to try again.
            if attempt >= MAX_ATTEMPTS:
                record(db, message_id, row.notice_id, "failed")
                return
            db.execute(text("UPDATE notice_messages SET status = 'queued' WHERE id = :id"),
                       {"id": message_id})
            db.commit()
            send_message.delay(message_id, attempt + 1)  # back of the queue, no countdown
            return
        record(db, message_id, row.notice_id, "sent", provider_id)


def record(db, message_id: int, notice_id: int, status: str,
           provider_id: str | None = None) -> None:
    db.execute(text(
        "UPDATE notice_messages SET status = :status, provider_message_id = :pid, "
        "sent_at = CASE WHEN :status = 'sent' THEN now() END WHERE id = :id"),
        {"status": status, "pid": provider_id, "id": message_id})
    db.commit()
    # A separate transaction, so it sees the records other processes committed.
    db.execute(FINISH_NOTICE, {"id": notice_id})
    db.commit()

5.4 Plan for repeat delivery and stopped workers

By default, Celery acknowledges a job just before it runs. With task_acks_late, the worker acknowledges after the task returns, so a job whose worker stops in the middle can be delivered again (Source 1). With the Redis broker, a job that is not acknowledged within the visibility timeout, 1 hour by default, is also delivered again (Source 2).

No job here is scheduled ahead with countdown or eta. Redis counts the visibility timeout from the moment a worker reserves the job, so a job reserved now to run more than an hour later is delivered a second time while the first copy is still waiting (Source 2). Scheduled notices wait in PostgreSQL with their send_at instead, and send_due_notices queues them when they are due. A retry after a connection error goes to the back of the queue with no delay.

A job delivered twice, or two runs at the same moment, are handled in four places:

  • send_message claims its record: UPDATE notice_messages SET status = 'sending' WHERE id = :id AND status = 'queued' RETURNING id. Two deliveries can run at the same time in the 2 processes; only one changes the status and gets the id back. The other gets no row and stops.
  • send_due_notices claims the notice with CLAIM_NOTICE, and send_notice runs the same statement, so a notice is queued once whether Send now, the scheduler or both start it.
  • QUEUE_MESSAGES inserts with ON CONFLICT (notice_id, user_id) DO NOTHING, so a repeat creates no second record for a recipient.
  • The provider is called after the claim is committed, with no transaction open. A record in "sending" is either being sent now or was left by a process that stopped during the call.

6.1 Rate limiting with a counter in Redis

Each staff member gets one counter per minute. Every request adds 1; above the limit, the API returns HTTP 429 with a Retry-After header. The counters live in Redis so that every API process sees the same count (Source 24 in the guide).

import time
from fastapi import Depends, HTTPException
from redis.asyncio import Redis
from app.auth import current_user
from app.settings import get_settings

# The second Redis instance, for counters and cache. Never the broker.
counters = Redis.from_url(get_settings().counters_url)


def per_minute(limit: int):
    async def check(staff=Depends(current_user)):
        window = int(time.time() // 60)
        key = f"rl:{staff.id}:{window}"
        count = await counters.incr(key)
        if count == 1:
            await counters.expire(key, 60)   # the counter deletes itself
        if count > limit:
            retry = 60 - int(time.time()) % 60
            raise HTTPException(429, "Too many requests",
                                headers={"Retry-After": str(retry)})
    return check

COUNTERS_URL is not a Stage 8 setting. It is added to the Settings class (counters_url) and to .env.example with the chatbot module, in the same pull request, and points at the second Redis instance described in 6.3.

Part 8

Read replicas and sharding

Both come after everything above has been tried, and most first applications need neither. User Notices marked both not needed: reads are small, the load test held, and one server holds the data.

8.1 When a read replica fits

All four must hold:

  1. The database server's CPU is the bottleneck under load.
  2. Most of that load is reads (pg_stat_statements, sorted by total time, shows SELECT statements at the top).
  3. Indexes, query changes and caching have been tried (Parts 4 and 6).
  4. The screens that would read from the replica can show data a moment old.

A replica does not help a write-heavy application. PostgreSQL standby servers accept read-only queries, and every write still goes to the primary (Source 18 in the guide).

8.2 Route reads in the application

Setting up streaming replication is server work, usually done with the database administrator. The application's part is to send each query to the right server.

from sqlalchemy.ext.asyncio import AsyncSession, create_async_engine
from app.settings import get_settings

settings = get_settings()
primary = create_async_engine(settings.database_url)
replica = create_async_engine(settings.database_replica_url)

async def write_session():
    async with AsyncSession(primary) as session:
        yield session

async def read_session():
    async with AsyncSession(replica) as session:
        yield session

DATABASE_REPLICA_URL is added to the Settings class and .env.example only when a replica is added, in that pull request. Not run: the test machine had no replica.

Routes that change data, and every read inside the same request as a write, use write_session. List and detail pages that can show slightly old data use read_session. Both engines count in the connection arithmetic in Part 7, each against its own server.

8.4 Sharding and partitioning

Sharding splits the data across several database servers. Every query then has to be sent to the server that holds its rows, which changes the data layer of the whole application. It applies when one primary cannot hold the data or the writes after every option above.

Partitioning is a different tool. It splits one table into parts on the same server and does not add capacity by itself (Source 17 in the guide). It helps when old rows are removed in bulk, or when queries read one part.

What PostgreSQL 18.6 answered in the test:

  • A primary key on id alone was refused: ERROR: unique constraint on partitioned table must include all partitioning columns, with DETAIL: PRIMARY KEY constraint on table "notice_messages" lacks column "notice_id" which is part of the partition key.
  • A record for a notice above every partition was refused: ERROR: no partition of relation "notice_messages" found for row. The next partition has to exist before its first notice, so a monthly migration or maintenance job adds it.
  • On 2,000,000 rows in two partitions, the claim by id alone searched the index of every partition (EXPLAIN showed an Index Scan on each, with Index Searches: 1002) and took 6.95 ms on October 15 and 22.9 ms on October 16, right after the rows were loaded. With WHERE notice_id = :notice_id AND id = :id it read one partition and took 0.031 ms and 0.066 ms. Once the table is partitioned, the send_message job carries the notice_id as well, and the claim uses both.
  • Detaching the oldest partition took 2 ms, and dropping it, with its 1,000,000 rows and three indexes, 101 ms. Deleting the same 1,000,000 rows from an unpartitioned copy of the table took 580 ms and left dead rows for VACUUM to reclaim (Source 17 in the guide).

Converting the existing table is a Stage 7 migration: create the partitioned table, copy the rows and switch the names, in a maintenance window. For User Notices this stays a scenario; the decision table in Part 10 records partitioning as not needed.

Answer

The job was delivered again after the restart, and the second copy found the record not yet marked sent, because the first copy had sent the SMS but not yet recorded it. Claim the record before calling the provider with UPDATE notice_messages SET status = 'sending' WHERE id = :id AND status = 'queued' RETURNING id, and stop when no row comes back. A second copy then sends nothing, and a record left in "sending" is checked against the provider's records before anything is sent again (5.4). The lab in Part 5 shows both runs: Deliver the same job twice with the claim on and off.

SCENARIO 5

Notice history is cached for 30 seconds. A staff member creates a notice, opens Notice history and does not see it. What happened, and what are the two fixes?

Answer

The page came from the cache, stored before the notice existed. Either delete the cache key when a notice is created, or shorten the expiry to what staff accept.

SCENARIO 6

Expected concurrency is 40. Errors start at 90 with "QueuePool limit of size 5 overflow 10 reached". pg_stat_activity shows 30 connections, and the slow query log shows GET /v1/notices taking 3 seconds. What do you fix first?

Answer

The slow query. It holds each connection for 3 seconds, so each process's pool of 15 runs out and later requests wait. Only 30 of 97 connections are in use, so the pool size is not the limit. Read the query's plan and fix it (Part 4), then rerun the test.

SCENARIO 7, SELF-CHECK 4 IN THE GUIDE

Billing and analytics both need every "notice sent" event, and analytics must be able to read last month's events again. Which option fits, and why not the Celery queue on Redis?

Answer

Kafka, or RabbitMQ streams. Each consumer group keeps its own position and messages are kept for a set period, so analytics can read last month's events again. A Celery queue on Redis gives each job to one worker and removes it once it is done, so a second system cannot receive it and nothing can be read again.

SCENARIO 8, SELF-CHECK 1 IN THE GUIDE

100,000 registered users, 40 concurrent requests, steady load. Which layers do you add before measuring?

Answer

None. Run the load test first. 40 concurrent requests at a steady rate may need no new layers, and the 100,000 registered users do not decide it: they are rows in the database, not load (1.1). User Notices, with 60,000 user records and 40 concurrent requests, added only the task queue, and for the bulk send rather than the steady load.

Connect the front end

Stage 6 connects each screen from Stage 1 to the backend functions from Stage 5, and makes sign-in work from end to end. When it is done, every screen is a page with a route, every page gets its data through an API call to /v1, and a list records what each page sends and reads. Stage 7 designs the tables from that list.

Basics

Server and Client Components

The rest of this page uses these three terms. If you know them, skip to Component tests.

Server Component

A component that runs on the Next.js server and sends finished HTML to the browser. In the App Router, components are Server Components unless marked otherwise.

Client Component

A component whose file starts with 'use client'. It also runs in the browser, so it can respond to clicks and typing. Forms and tables that change on the page are Client Components.

Route handler

A route.ts file that answers HTTP requests on the Next.js server, like a small API endpoint.

In User Notices, the pages that call the backend are Client Components, and so is NoticeForm. The root page, app/page.tsx, is a Server Component: it runs on the server and only redirects.

A component test renders one shared component in a simulated browser (jsdom) and uses it the way a staff member would. It needs no backend and runs in seconds, so CI runs it on every push. Run these in frontend/. The second line is the guide's install command (vite-tsconfig-paths resolves the imports that start with @/), and the third adds "test": "vitest" to package.json. Version 24 matches the Node.js 24 LTS runtime.

How a request travels

      
A page never calls fetch directly. A Client Component calls api() in lib/api.ts, which sends the request to /v1 with the session cookie. A Server Component calls apiServer() in lib/api-server.ts, which uses API_INTERNAL_URL and passes the cookie on. Either way, the backend checks the cookie through current_user before it calls the service. The sandbox is a second copy of the deployment, used for testing, set up in Stage 9; live is the copy the staff use. Pick a situation, then step through it.

Two settings produce this. NEXT_PUBLIC_API_BASE starts with NEXT_PUBLIC_, so Next.js copies its value into the browser code when the build runs. It is set only in .env.development, which npm run dev loads, so the release build has an empty value and the browser calls the relative path /v1. The same build then runs in the sandbox and in live. API_INTERNAL_URL has no prefix: it stays on the Next.js server and is read when the code runs, from .env.development in development and from the user-notices-web unit on the servers. It can use 127.0.0.1 because the Next.js server passes the session cookie on itself; the browser's address stays localhost so that the cookie's host matches.

The session cookie's settings

      

        
HttpOnly
JavaScript on the page cannot read the cookie; only the server receives it. A script injected through a bug cannot copy the session.

        
SameSite=Lax
The browser does not send the cookie with requests started by other sites, except when a visitor follows a link to the application. Lax is also the default when the attribute is missing.

        
Secure
The cookie is sent over HTTPS only. Browsers allow plain HTTP on localhost, except Safari, so the route sets Secure only when ALLOWED_ORIGIN starts with https://, as it does in the sandbox and live. No separate setting is needed.

      

      
In development the cookie is set by the backend on port 8000 and read by proxy.ts on port 3000. That works because cookies are scoped by host name, not by port.

    frontend/proxy.ts
    
          
    import { NextResponse } from 'next/server'
import type { NextRequest } from 'next/server'

export function proxy(request: NextRequest) {
  if (!request.cookies.has('session')) {
    return NextResponse.redirect(new URL('/login', request.url))
  }
  return NextResponse.next()
}

export const config = { matcher: ['/users/:path*', '/notices/:path*'] }
    
          
    Next.js 16 renamed this file convention from middleware to proxy. The file sits at the root of frontend/, beside app/. The Next.js documentation advises against relying on proxy alone and says to verify authentication in the code that handles the data, which here is the backend.
    
          
    CVE-2025-29927In March 2025 a flaw in Next.js middleware let a request skip the middleware's checks by sending an internal header, x-middleware-subrequest. Self-hosted applications run with next start or the standalone output were affected, which is how User Notices runs in Stage 9; applications hosted on Vercel were not. Next.js 15.2.3, 14.2.25, 13.5.9 and 12.3.5 fixed it, and Next.js 16 is outside the affected versions (GitHub Advisory Database, Vercel postmortem). It is one reason the backend checks the token itself: a request that skipped proxy.ts still gets 401 from current_user for any data.

      The rules behind the simulator
      
      
        
        
      • Exact origin. http://localhost:3000, not localhost:3000, not http://localhost:3000/, and not https.
        • 
        
      • No wildcard with credentials. FastAPI's documentation says allow_origins, allow_methods and allow_headers cannot be ["*"] when allow_credentials is True; each has to be listed.
        • 
        
      • Both sides opt in. The backend allows credentials, and the page's fetch sends them (credentials: 'include' in api()). Either one alone leaves the cookie out.
        • 
        
      • Preflight. A POST with a JSON body, or any PATCH, makes the browser ask first with OPTIONS. A GET with no body goes out directly, and the browser checks the CORS headers on the response.

        Developer A clears a CORS error by setting allow_origins=["*"]. Why is that the wrong fix?
        FastAPI's documentation does not allow a wildcard origin together with allow_credentials=True. A server that answers every origin and allows credentials lets pages from any origin make calls that carry credentials. List http://localhost:3000.
        
        
        proxy.ts lets a visitor open /users because a session cookie exists, but the token expired yesterday. What does the visitor see?
        The page opens, its first API call returns 401 from current_user, and the 401 branch in api() sends the visitor to /login.
        
        
        In the sandbox, nginx serves the pages and /v1 from one address. Does the browser apply CORS there?
        No. The page and the API share one origin, so there is no cross-origin request. The middleware stays, with ALLOWED_ORIGIN set to the site's own address.
        
        
        The New notice page sends text, group_id and send_at. Where does the notice's author come from?
        From the backend: the route takes the signed-in staff member from current_user. A value sent by the page can be changed by whoever uses the page.
        
        
        Why does UserTable receive its users as a prop instead of calling the API itself?
        The page owns the call and its loading and error states. The component can be reused on other pages and checked with sample data.
        
        
        The User detail page works with npm run dev. After the release build, which address does it call?
        The relative path /v1. NEXT_PUBLIC_API_BASE is http://localhost:8000 in .env.development and empty in the release build, because its value is fixed into the code when the build runs. nginx sends /v1 to the backend.
        
        
        Guide self-check. The browser console shows a CORS error when the Users list loads. Which side do you change, and what do you change?
        The backend. Add the front end's origin to the allowed origins in the CORS middleware (ALLOWED_ORIGIN in .env). The browser enforces the rule, but only the backend can allow the origin.
        
        
        Guide self-check. Why does the front end guard its routes if the backend checks the token on every call?
        The guard sends a visitor who is not signed in to the sign-in page instead of showing pages that fail. It does not protect the data. The backend's check on every call does.

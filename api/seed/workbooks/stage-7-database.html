Step 1 of 7

Fields

The field inventory is a table with one row per value the application stores. It is finished before any table is designed, because the tables are groupings of these rows.

Do

  1. Open the Stage 6 route list. For each screen, write down every field the page sends (request body and query string) and every field it shows.
  2. Open each Stage 5 function comment and store method. Add every value it reads or writes that no screen shows, such as the author of a notice, a status, or the provider's message ID.
  3. Add what Stage 1 says must be logged and audited. For User Notices, that is one send record per message, and one audit row for each sign-in, denied request, change to a user or staff account, and send (Step 3 lists the events).
  4. For each field, record its name, where it comes from, its type, whether it is required, its rules (unique, allowed values, format, length) and the concept it describes: a staff account, a user, a notice, an audit row.
  5. Mark values that can be computed from other fields, such as a count. These are derived and are not stored.
  6. Remove any field that no screen, no function and no logging or audit requirement uses.

Done when

  • Every field each screen sends or shows appears in the inventory.
  • Every value each function reads or writes appears in the inventory.
  • Every value Stage 1 says must be logged or audited appears in the inventory.
  • Each row has a type, a required flag, its rules and a concept.
  • Derived values are marked, and no row lacks a source.

Watch for

  • Passwords. Store the hash. The password itself is never written to the database, the log or an audit row.
  • Phone numbers. Store them as text in international format. A number type drops the +, and phone numbers are never calculated with.
  • Stored counts. A count kept in its own column can come to disagree with the records it counts. Count when reading, and store a count only if Step 4 measures the read as slow.
  • Time without a time zone. A send time is an instant. Use timestamp with time zone: PostgreSQL stores it in UTC, and an input with no time zone is read in the connection's TimeZone setting, which may not be the one the user meant (Source 3).
  • Audit details. List what an audit row records, and what it leaves out: passwords, session tokens and other secrets never go in, and personal data such as phone numbers is masked (Source 23).
  • Fields for later. A column that no screen or function uses is a guess. Add it with a migration when a requirement needs it.

Step 2 of 7

Tables and columns

Each concept in the inventory becomes one table, with an identity primary key and a foreign key for every reference. Every column gets a type, NOT NULL where a value is required, a default where one applies, and the constraints that keep wrong values out, so the database rejects a bad row whatever code writes it.

BasicsSchema terms

Column type
The kind of value a column holds: text, a whole number, a point in time.
NULL
No value. NOT NULL means the column must always have one.
Default
The value used when an insert gives none.
Constraint
A rule the database checks on every insert and update: PRIMARY KEY, NOT NULL, UNIQUE, CHECK and FOREIGN KEY.
Role
A database account, unrelated to the staff roles (editor, viewer) in User Notices. The role that owns the tables and the role the application logs in as can be different.
Transaction
A group of statements that the database saves together, or not at all.
Trigger
A function the database runs on every insert, update or delete on a table.
Migration
One file that changes the schema. Its upgrade function makes the change, and its downgrade function reverses it.
Revision and head
The id Alembic gives each migration, and the newest revision. Each migration names the one before it in down_revision.
Round trip
Upgrade, downgrade, then upgrade again, to show that both directions work.
Rollback
Going back to the previous release of the code (Stage 9).

Do

  1. Group the inventory rows by their Concept column. Each concept is one table.
  2. Apply the one-concept test: every column must describe the thing the row's id identifies. A column that describes something else belongs in another table.
  3. Give each table an id primary key of type bigint GENERATED ALWAYS AS IDENTITY. The database assigns every value and refuses an insert that supplies its own (Source 2).
  4. Turn each reference into a foreign key column named after the table it points to: group_id, author_id. Set ON DELETE RESTRICT on each. A record that links two concepts and has fields of its own, such as a send record, is its own table with a foreign key to each.
  5. Give each column a type from the table in Going deeper: Schema details. Make it NOT NULL unless it stays empty until something happens, such as sent_at, and give it a default where one applies.
  6. Add the constraints: UNIQUE where duplicates are wrong, and CHECK for allowed values, formats and lengths. Give every constraint a name (Source 1).
  7. Write the tables as SQLAlchemy models in app/db/models.py, with the naming convention set on the metadata. Name any index or unique constraint on more than one column in the model yourself.

Naming: tables in lower case with underscores, foreign key columns named after the table they point to (group_id), and a name for every constraint and index. The convention's ix and uq names use the first column only (column_0_label, column_0_name), so an index or unique constraint on more than one column is named in the model: ix_notices_status_send_at, ix_audit_log_entity, ix_audit_log_staff_id and uq_notice_messages_notice_id_user_id.

Watch for

  • Rules only in the service. The service checks the input; the constraints stop a bad row from any other path, such as a script or a future endpoint. The schema tests in Step 7 confirm the database rejects an unknown group, empty text, text over 640 characters, a phone number without +, an email with capitals, an unknown role, and deleting a user who has send records.
  • ON DELETE CASCADE on a log. Cascading from users to notice_messages would delete a user's send records with the user, and cascading from staff to audit_log would delete the audit trail of a removed account. RESTRICT refuses the delete while rows point to it (Source 1).
  • GENERATED BY DEFAULT. It lets an insert supply its own id, and the sequence does not move past it. On the test machine, a BY DEFAULT table took an insert with id 1, and the next insert without an id failed with: duplicate key value violates unique constraint "by_default_pkey". With ALWAYS, the typed id is refused instead: cannot insert a non-DEFAULT value into column "id".
  • A CHECK on status. Adding a new status later takes a migration that changes the constraint. A new status is also a change the front end and the Stage 3 API rule must account for.
  • Constraints without names. Set the naming convention before the first migration. Renaming constraints after they exist is a migration of its own. An index or unique constraint on more than one column needs its name in the model; otherwise the convention names it after its first column only.

Why is notice_messages its own table?

The one-concept test. A message's status and provider ID describe that message; on the notice row they would repeat the notice's text and send time once per user.

A user with send records is deleted. The foreign key is ON DELETE RESTRICT. What happens?

Text with a CHECK keeps the exact value and rejects a value in the wrong format. In Step 7, ck_users_phone_format rejected 5125550104. This is self-check 4 from the guide.

Audit trail

The audit table records who did what to which record, when, from where, and with what result. The application adds and reads its rows but cannot change or delete them, because the role it logs in as has only SELECT and INSERT on the table.

Other terms this step uses:

Request id
A random id the backend gives each request. It appears on every log line for that request, in the X-Request-ID response header and in each audit row the request writes, so the three can be matched.
Middleware
Code that runs around every request, before and after the route function.
Privilege
What a database role may do to a table, such as SELECT, INSERT, UPDATE, DELETE or TRUNCATE. GRANT gives a privilege and REVOKE takes it away (Source 20).
Masking
Keeping only part of a value, such as the last four digits of a phone number: xxx4417.

Step 4 of 7

Views

A plain view is a saved query: PostgreSQL runs its query every time the view is read (Source 4). It gives a page one name to read from; it does not make the query faster. Measure the view's query at the expected data size, fix the query if it does work the page does not need, and use a materialized view only when the result may be out of date for a while. PostgreSQL updates a materialized view only when REFRESH MATERIALIZED VIEW runs, so the refresh has to be scheduled (Source 5).

Do

  1. List the queries that join tables and are used in more than one place, or that a page needs in a shape no single table has.
  2. Write each one as a plain view. Alembic does not create views from models, so the view and its GRANT go into the migration by hand in Step 6.
  3. Load test data at the size you expect after a year of use, inserted in the order the application writes it, then run VACUUM (ANALYZE) and time the view with EXPLAIN ANALYZE.
  4. If the time is too long for the page, read the plan. Look first for work the page does not need, such as rows that are computed and then discarded.
  5. Use a materialized view only when the query is still slow after that and the page can show results from the last refresh. Give it a unique index and a refresh schedule.

Indexes

Every index in the schema names the query it serves. Primary keys and unique constraints are indexed automatically (Source 18); foreign key columns are not (Source 1), so each one gets an index unless an existing index already starts with that column.

Do

  1. List every query the application runs: each store method, the support queries on audit_log, and any query a later stage already needs, such as the scheduler's search for notices due to send.
  2. For each query, write down the columns in its WHERE, JOIN and ORDER BY clauses.
  3. Cross off what is already indexed: primary keys, unique constraints, and the leading column of any multicolumn index.
  4. Add an index on each remaining foreign key column and each column the frequent queries filter or join on.
  5. Use a multicolumn index only when a frequent query constrains its first column. PostgreSQL advises using them sparingly; a single-column index is usually enough (Source 7).
  6. With test data loaded and VACUUM (ANALYZE) run, check each query with EXPLAIN. The index name should appear in the plan.
  7. Remove any index that no query uses. Each index adds work to every insert, update and delete, and takes storage (Source 6).

Going deeperChanging a schema that is in use

    
During a deploy, and after a code rollback, one version of the code runs against the schema left by the other version's migrations. A migration is safe when the code before it and the code after it both work with the schema it leaves. Changes that would break the older code are split across releases: first expand (add the new structure and use it alongside the old), then contract (remove the old structure once nothing uses it). This is called expand and contract, or parallel change (Source 25).

    

      
ChangeReleasesHow

      
        
Add a tableOneThe older code ignores it

        
Add a column that may be empty, or has a defaultOneThe older code ignores it

        
Add an indexOneOn a large table in use, build it with CREATE INDEX CONCURRENTLY, so writes continue while it builds. It cannot run inside a transaction, so in Alembic the op.create_index call with postgresql_concurrently=True goes inside a with op.get_context().autocommit_block(): block (Sources 26 and 27)

        
Make an existing column NOT NULLTwoRelease 1 writes the value everywhere and fills in the old rows; release 2 adds NOT NULL

        
Rename a column, or change its typeFourExpand, migrate, stop writing, drop. See the scenario below

        
Remove a column or a tableTwoRelease 1 stops using it; release 2 drops it, after a backup

      
    

    
Default. Write each migration so that the release before it and the release after it both work with the schema it leaves. When a change would break the older code, split it into expand and contract.

The guide's Stage 7 self-check
Six questions

    

      
Each question also appears as a quiz in the step it belongs to.

      
1. A teammate adds a plain view to make the Notice history page faster. Will it work?
No. A plain view is a saved query and runs the same query each time. If the page is measured as slow, an index or a materialized view with a scheduled refresh is the fix. In Step 4, a rewritten query took Notice history from 71 to 95 ms down to 6.6 to 7.7 ms at test size.

      
2. Which columns in notice_messages need an index that you have to create yourself?
notice_id and user_id are foreign key columns, which PostgreSQL does not index automatically. In the example, the unique (notice_id, user_id) constraint already gives notice_id an index through its leading column, so only user_id needs an index of its own. The id column is the primary key and is already indexed.

      
3. The users table needs a new column. How is it added?
With a new Alembic migration, applied in the sandbox and then in live as part of the deploy. Add the column to the model, autogenerate, review, apply and run the round trip. A required column on a table with rows takes a default, or two releases (Step 6).

      
4. Why is users.phone stored as text with a CHECK, and not as a bigint?
A phone number starts with a +, which a number type drops, and phone numbers are never calculated with. Text with a CHECK keeps the exact value and rejects a value in the wrong format. In Step 7, ck_users_phone_format rejected 5125550104.

      
5. A release renames a column in its migration and uses the new name straight away. The release is rolled back. What fails, and how should the rename have been done?
The previous release reads and writes the old column name, which no longer exists, so its queries fail. The rename should have used expand and contract: add the new column and write both, read the new one, stop writing the old one, and drop it in a later release. Step 6 runs these four releases for users.phone.

      
6. Which database roles write audit rows, and which privileges do they have on audit_log?
usernotices_app_a or usernotices_app_b, the roles the application logs in as. They are members of usernotices_app, which has SELECT and INSERT on audit_log and no UPDATE, DELETE or TRUNCATE. usernotices_owner owns the table and runs the migrations. The privilege test in Step 3 shows all three refused.

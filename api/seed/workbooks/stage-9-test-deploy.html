Order of the work
  1. Part A (test) starts with the first commit of Stage 9 and then runs on every push.
  2. Parts B and C (release, server and services) are set up once on the sandbox server, then repeated on the live server.
  3. Part D (before the first user) is done on both servers before anyone signs in to live. The backups copied off the server and the restore test are done on live.

Part A

Test

Each layer of User Notices has its own kind of test, and each test runs at a fixed point: on every push, after each merge to main, each weekday night, at each deploy, or before a release. The Basics, Going deeper and Scenario blocks are the guide's. Tasks A1 to A11 build each kind of test for User Notices and show what it printed on the test server.

Basics

Kinds of test

  • Unit test. One function on its own, with what it depends on replaced by stubs. It runs in milliseconds.
  • API test. Calls one endpoint and checks the status code and the response, including what happens for a caller who is not allowed.
  • Integration test. Several real parts together, such as the backend with a real PostgreSQL.
  • Component test. One front end component, rendered and used the way a person would use it.
  • End-to-end test. A real browser drives the whole application, from sign-in to the result on the screen.
  • Migration test. Runs the migrations up and down against a database.
  • Smoke test. A few quick calls right after a deploy, to show that the release serves its main screens.
  • Contract test. Checks that the API still returns what a known client relies on.
  • Property-based test. Generates many inputs from a description, such as the OpenAPI document, and looks for failures.
  • Functional testing. People work through scenarios against the requirements.
  • Regression run. The whole suite, run after a change, to find what broke elsewhere.

A2. Unit and API tests

Do
  1. From backend/, run python -m pytest -q tests/test_notices.py and confirm the Stage 5 unit tests pass. They use InMemoryNoticeStore and FakeSmsClient from tests/stubs.py, so they need no database.
  2. Write API tests for each endpoint with FastAPI's TestClient. To act as a viewer or an editor without signing in, set app.dependency_overrides[current_user] to a function that returns a Staff, and clear the overrides after the test (Source 97).
  3. For each endpoint that changes data, test that a viewer gets 403, and test each validation rule (422).
  4. Add the endpoint access test below. It calls every endpoint without a session and fails if any endpoint other than sign-in and the health check answers with anything but 401.
  5. Remove the sign-in dependency from one endpoint, run the access test, and confirm it fails. Put the dependency back. This shows the test checks something.

Example: every endpoint requires sign-in
tests/test_endpoint_access.py
# tests/test_endpoint_access.py
# Every endpoint must refuse a caller who is not signed in, except the ones listed in PUBLIC.
import re
from fastapi.testclient import TestClient
from app.main import app

PUBLIC = {("POST", "/v1/auth/login"), ("GET", "/v1/health")}
METHODS = {"get", "post", "put", "patch", "delete"}


def test_every_other_endpoint_requires_sign_in():
    # A server error counts as reachable too, so report it instead of raising it
    client = TestClient(app, raise_server_exceptions=False)
    checked, exposed = 0, []
    # The OpenAPI document lists every endpoint the application serves
    for path, operations in app.openapi()["paths"].items():
        for method in operations.keys() & METHODS:
            if (method.upper(), path) in PUBLIC:
                continue
            url = re.sub(r"\{[^}]+\}", "1", path)   # /v1/users/{user_id} becomes /v1/users/1
            status = client.request(method.upper(), url, json={}).status_code
            checked += 1
            if status != 401:
                exposed.append(f"{method.upper()} {path} returned {status}")
    assert checked > 0, "No endpoints were checked"
    assert exposed == [], "Reachable without sign-in: " + "; ".join(exposed)

With staff: Staff = Depends(current_user) removed from list_notices in routers/notices.py, the test failed with:

Output
AssertionError: Reachable without sign-in: GET /v1/notices returned 500

The status is 500 because the test's DATABASE_URL points at an address where no database listens. The endpoint answered without asking for a session, which is the fault the test looks for. raise_server_exceptions=False makes TestClient return the 500 instead of raising the database error, so the test reports the endpoint.

The test reads the OpenAPI document rather than app.routes. In the FastAPI version used here (0.143.2), each router added with include_router appears in app.routes as one entry for the whole router, so a loop over app.routes found no endpoints and passed without checking anything. The checked > 0 line stops that from happening silently.

Done when
  • Every endpoint has API tests for its status codes, its validation, and a viewer denied each change
  • The access test passes on main, and was seen to fail once with a dependency removed
Watch for
  • An endpoint declared with include_in_schema=False is not in the OpenAPI document, so the access test does not see it. Add any such endpoint to the test by hand.
  • Adding an endpoint to PUBLIC to make the test pass. Each entry needs a reason and a reviewer.
  • dependency_overrides left in place after a test. Every later test then runs as that staff member. The as_viewer fixture clears it.

A3. Integration and migration tests

Do
  1. Install Docker on each developer's machine and on the CI runner. Testcontainers starts PostgreSQL 18 in a container for the test session and removes it afterwards (Source 98).
  2. Add the fixtures below to tests/conftest.py. The database fixture prepares the container the way a server is prepared: deploy/bootstrap.sql as the superuser creates the roles and the database, then alembic upgrade head runs as usernotices_owner (Stage 7).
  3. Connect the tests as usernotices_app_a, the application's role, and write the test rows as the owner. A missing GRANT then fails the test, as it would in live.

Part B

Build the release and prepare the server

CI builds one release file from each merge to main, and that same file goes to the sandbox and, once promoted, to live. Each server is prepared once, so that each service runs under its own account and cannot change its code, the secrets are readable only by root, and releases arrive without a personal credential.

Basics

Server terms

  • root and sudo. root is the administrator account on a Linux server. sudo runs one command as root, or as another account with -u.
  • Owner, group and mode. Every file has an owner and a group. Its mode says what the owner, the group and everyone else may do with it: read, write, or run (execute). In a mode such as 640, 6 is read and write, 4 is read only, and 0 is no access (Source 107).
  • Symbolic link. A file that points to another file or folder. /opt/user-notices/current is one.
  • systemd unit. A file in /etc/systemd/system/ that tells systemd how to start one service. systemctl start, stop, restart and status act on it, and journalctl -u shows its output.
  • Port and 127.0.0.1. A service listens on a port number. A service bound to 127.0.0.1 can be reached only from the same server.
  • SSH key. A pair of files used to log in without a password. The private key stays with the person or the pipeline; the public key goes on the server.
  • TLS certificate and private key. The certificate shows browsers the server's name. The private key stays on the server and proves that the server holds the certificate.
  • Firewall. Rules on the server that decide which ports other machines can reach.

B1. Build the release in CI

Do
  1. In the front end, set output: 'standalone' in next.config.ts. next build then writes a server.js with only the packages it needs, so the server needs Node.js but no npm install (Source 123).
  2. Add scripts/build_release.sh. It names the build by its commit, packs the backend code with requirements.txt and a wheels/ folder of every pinned package, and the front end's standalone build with public/ and .next/static/ copied into it.
  3. Run CI on a self-hosted GitHub Actions runner on the sandbox server, so the runner has the same Ubuntu release and Python version as the live server (Ubuntu 24.04 and Python 3.14). Packages with compiled parts, such as psycopg-binary and pydantic-core, have a separate wheel for each Python version. The runner can reach the sandbox and live servers; a runner outside the data center could not. The runner needs Docker for the integration tests (A3).
  4. Add .github/workflows/sandbox.yml. On each merge to main, it runs the regression run (A9), builds the release once, keeps the file and its checksum as a workflow artifact for 90 days, deploys it to the sandbox, and runs the end-to-end tests there (A6).
  5. Leave the version out of the build. A build gets a version only when it is promoted: its commit is tagged v1.5.0, and live unpacks it into releases/1.5.0 (F2). In the sandbox, the release folder has the build's name.

#!/usr/bin/env bash
# scripts/build_release.sh: builds one release from the commit that CI checked out.
# The runner has the same Ubuntu release and Python version as the servers, because some
# wheels are compiled for one Python version.
set -euo pipefail
cd "$(dirname "$0")/.."

BUILD=$(git rev-parse --short=7 HEAD)
OUT=dist/user-notices-$BUILD
rm -rf dist && mkdir -p "$OUT/frontend"

# Backend: committed files only (never .env), and every pinned dependency as a wheel
git archive HEAD backend/app backend/migrations backend/alembic.ini backend/requirements.txt |
  tar -x -C "$OUT"

cp -r frontend/.next/static "$OUT/frontend/.next/static"
cp -r frontend/public "$OUT/frontend/public"

printf 'build=%s\ncommit=%s\nbuilt=%s\n' "$BUILD" "$(git rev-parse HEAD)" "$(date -u +%FT%TZ)" \
  > "$OUT/RELEASE"

(cd dist && sha256sum "user-notices-$BUILD.tar.gz" > "user-notices-$BUILD.tar.gz.sha256")

Example: the sandbox workflow

The original practice used Azure DevOps. User Notices uses GitHub Actions on the self-hosted runner, and each step calls a script from the repository.

.github/workflows/sandbox.yml
# .github/workflows/sandbox.yml: every merge to main is tested, built once, deployed to the
# sandbox, and checked there in a browser.
name: sandbox
on:
  push:
    branches: [main]

concurrency: sandbox        # one sandbox deploy at a time

jobs:
  build-and-deploy:
    runs-on: [self-hosted, linux, user-notices]
    environment: sandbox
    steps:
      - uses: actions/checkout@v5
      - name: Install
        run: |
          python3.14 -m venv backend/.venv
          backend/.venv/bin/pip install -r backend/requirements.txt -r backend/requirements-dev.txt
          cd frontend && npm ci
      - name: Regression run, without the browser tests
        run: scripts/regression.sh
      - name: Build the release
        id: build
        run: echo "build=$(scripts/build_release.sh | tail -n 1)" >> "$GITHUB_OUTPUT"
      - uses: actions/upload-artifact@v4
        with:
          name: release-${{ steps.build.outputs.build }}
          path: dist/user-notices-${{ steps.build.outputs.build }}.tar.gz*
          retention-days: 90
      - name: Deploy to the sandbox
        env:
          BUILD: ${{ steps.build.outputs.build }}
          DEPLOY_SSH_KEY: ${{ secrets.DEPLOY_SSH_KEY }}
        run: |
          key=$(mktemp) && trap 'rm -f "$key"' EXIT
          printf '%s\n' "$DEPLOY_SSH_KEY" > "$key"
          target=usernotices-deploy@notices-sandbox.example.internal
          scp -i "$key" "dist/user-notices-$BUILD.tar.gz" "dist/user-notices-$BUILD.tar.gz.sha256" \
              "$target:/opt/user-notices/incoming/"
          ssh -i "$key" "$target" sudo /usr/local/sbin/user-notices-deploy "$BUILD"
      - name: End-to-end tests against the sandbox
        env:
          E2E_BASE_URL: https://notices-sandbox.example.internal
          E2E_EMAIL: ${{ secrets.E2E_EMAIL }}
          E2E_PASSWORD: ${{ secrets.E2E_PASSWORD }}
        run: cd frontend && npx playwright test

The workflows were checked with actionlint, which also runs shellcheck on every run step, and passed. They were not run on GitHub; the scripts they call were run on the test server.

  • The RELEASE file names the commit the build came from
Watch for
  • Building a release on a developer's laptop. It can include files that were never committed.
  • Building on a different Python version from the servers. The install on the server then fails with No matching distribution found.
  • Forgetting to copy .next/static and public. Pages load without their scripts and styles, and requests under /_next/static return 404.
  • Building again for live. A new build is a new release that nobody tested, even from the same commit.

Preparing the server

Once per server, before the first deploy, as root:

  1. Install the operating system release from the Stage 3 version table. Ubuntu 24.04's own packages hold older releases of most of the other tools, so each comes from its project, at the version the table records: PostgreSQL 18 from the PostgreSQL apt repository (Source 156); Redis 8 from Redis's apt repository, which installs the redis package and the redis-server service (Source 157); Python 3.14 built from source with make altinstall (Source 158), or installed with uv python install 3.14 (Source 159); Node.js 24 as the prebuilt Linux binary from nodejs.org (Source 8) or from the NodeSource apt repository (Source 160). nginx comes from Ubuntu's own package, version 1.24 (Source 155).
  2. Create an account for each service that needs different access: useradd --system --no-create-home --shell /usr/sbin/nologin usernotices (the API, the workers and the scheduler), and the same for usernotices-web (the front end). A process can read the environment of other processes under the same account, so the front end, which needs no secrets, does not share the backend's account. On both servers, create usernotices-deploy, the account the pipeline logs in as to deliver releases; on the live server, also create usernotices-backup, the account the backup server logs in as to read the dumps. These two log in over SSH with a key that is limited to one command, so they need a shell: useradd --system --create-home --shell /bin/sh usernotices-deploy, and the same for usernotices-backup.
  3. Create the folders: install -d -o root -g root -m 755 /opt/user-notices /opt/user-notices/releases, install -d -o usernotices-deploy -g usernotices-deploy -m 750 /opt/user-notices/incoming, and install -d -o root -g root -m 700 /etc/user-notices. Allow the deploy account to run the deploy script, and nothing else, as root, with one line in /etc/sudoers.d/user-notices: usernotices-deploy ALL=(root) NOPASSWD: /usr/local/sbin/user-notices-deploy
  4. In /etc/redis/redis.conf, set bind 127.0.0.1, maxmemory-policy noeviction, appendonly yes and a password with requirepass, then systemctl restart redis-server.
  5. Create the database and the roles from deploy/bootstrap.sql (Stage 7), and set each role's password with psql's \password command.
  6. Allow SSH only from the administrators' network, the CI runner and the backup server, and ports 80 and 443 from everywhere, through the firewall. With ufw, for an administrators' network of 10.20.0.0/24: ufw allow from 10.20.0.0/24 to any port 22 proto tcp, the same line for the runner's and the backup server's addresses, ufw allow 80/tcp, ufw allow 443/tcp, then ufw enable.
  7. Put the secrets files in /etc/user-notices/ and the TLS certificate and key in /etc/ssl/, copied from the organization's secret store.

systemd's documentation says environment variables are not suitable for secrets, because other processes can see them and they pass down to child processes. In each unit, ProtectSystem=strict makes most of the file system read-only for the service, apart from the paths in ReadWritePaths= and the folders systemd creates for it with StateDirectory= and CacheDirectory=.

Default. An EnvironmentFile with mode 600, as in the Example. Use LoadCredential= when the organization's rules do not allow secrets in environment variables.

Before the service starts, systemd copies the file into a folder that only the service and root can read, and passes the folder's path in the CREDENTIALS_DIRECTORY environment variable; the secret's value is never in the environment. pydantic-settings reads one file per setting from a folder given as secrets_dir, so Settings(_secrets_dir=os.environ["CREDENTIALS_DIRECTORY"]) loads them. User Notices uses the default. This alternative was not run, because the test server has no systemd.

    Steps 1 to 3 change nothing users see: the new release is unpacked in its own folder, and only the workers and beat stop. Users are interrupted from step 4 until step 7 completes. If the migration in step 5 fails, PostgreSQL rolls it back and the script starts the previous release unchanged. If the checks in step 8 fail, the script switches the link back and starts the previous release; the migration from step 5 stays applied, which is why every migration follows expand and contract.

    Example: the eight steps (the guide's list)
    1. Unpack the release from /opt/user-notices/incoming/ into /opt/user-notices/releases/1.5.0/, create the virtual environment in the release folder with python3.14 -m venv, install the wheels with the environment's pip install --no-index --find-links wheels -r requirements.txt, compile the bytecode cache with the environment's python -m compileall -q app (the service cannot write to the release folder, so the cache is written now), and then set the owners and modes from the permissions table.
    2. Stop the beat and worker services. Celery finishes the tasks in progress, and queued jobs stay in Redis.
    3. Back up the database: sudo -u postgres pg_dump --format=custom --file=/var/backups/user-notices/before-1.5.0.dump usernotices.
    4. Stop the front end and the API.
    5. Record the current revision with alembic current, then run alembic upgrade head from the new release's backend folder, as usernotices_owner, with the connection string from /etc/user-notices/migrate.env. Alembic runs the upgrade in a transaction, so if a migration fails, PostgreSQL rolls it back; the script then starts the previous release unchanged and stops.
    6. Switch the link: ln -sfn /opt/user-notices/releases/1.5.0 /opt/user-notices/current.
    7. Start the API, the front end, the workers and beat.
    8. Call GET /v1/health every 5 seconds for up to 60 seconds, then sign in with the account in /etc/user-notices/smoke.env and call GET /v1/users. If either fails, switch the link back and start the previous release.

    deploy.sh --rollback runs steps 2, 4, 6 and 7 for the previous release, so the workers and beat also go back to the previous code. A switch back runs the previous code against the migrated schema, so every migration follows expand and contract. Users are interrupted from step 4 until step 7 completes, within the 5 minutes Stage 1 allows.

    What the script does beyond the eight steps:

    • It checks the file against its checksum before unpacking, and refuses a release folder that already exists, so a version is never unpacked over itself.
    • It names the release folder by the version when one is given (live) and by the build otherwise (the sandbox).
    • It sets PATH itself, so it finds the system's python3.14 and systemctl whether sudo or a root shell runs it.
    • Step 1 compiles the bytecode cache with python -m compileall -q app before the owners change. The service's account cannot write to the release folder, so Python could not write the cache later; without it, each process would compile the modules again at every start.
    • Step 1 then gives the backend to root:usernotices and the front end to root:usernotices-web, and chmod -R u=rwX,g=rX,o= makes folders 750, files 640 and the programs in .venv/bin 750.
    • Step 3 sets the dump's mode to 640. On the test server, the first dumps were 664, because the PAM session that sudo opens gave postgres a umask of 002.
    • Step 5 writes the revision before the migrations to /opt/user-notices/previous-revision and to deploy.log. Stage 10 uses it to undo a migration.
    • Step 7 uses systemctl restart, which starts a stopped service and restarts a running one.
    • --rollback runs steps 2, 4, 6 and 7 for the release named in /opt/user-notices/previous, then the step 8 checks, and logs rollback healthy or rollback UNHEALTHY.
    • After step 8, it keeps the five newest release folders, and never removes current or previous.

    The expand and contract rule

    A migration that removes or renames something the previous release needs breaks the previous release, so a rollback would fail. Split such changes over two releases.

    ChangeRelease N (expand)Release N+1 or later (contract)
    Add a required columnAdd it as nullable; the new code writes itFill the old rows, then set NOT NULL
    Rename a columnAdd the new column; the code writes both and reads the new oneDrop the old column
    Remove a columnThe code stops reading and writing itDrop the column
    Rename a task or change its argumentsAdd the new task; the code queues the new one, and the workers run bothRemove the old task, once no job of the old form is queued

import asyncio
from fastapi import APIRouter
from fastapi.responses import JSONResponse
from redis.asyncio import Redis
from sqlalchemy import text
from app.db.session import engine
from app.settings import settings

router = APIRouter(prefix="/health", tags=["health"])

async def database_ok() -> bool:
    try:
        async with asyncio.timeout(2):
            async with engine.connect() as conn:
                await conn.execute(text("SELECT 1"))
        return True
    except Exception:
        return False


async def redis_ok() -> bool:
    try:
        async with asyncio.timeout(2):
            return bool(await redis_client.ping())
    except Exception:
        return False


@router.get("", responses={503: {"description": "The database or Redis is not reachable"}})
async def health() -> JSONResponse:
    # No sign-in needed: the deploy script and monitoring call this.
    # Reports only ok or failed for each part, never connection details.
    database, redis = await asyncio.gather(database_ok(), redis_ok())
    healthy = database and redis
    body = {"status": "ok" if healthy else "failed",
            "database": "ok" if database else "failed",
            "redis": "ok" if redis else "failed"}
    return JSONResponse(body, status_code=200 if healthy else 503)

    Basics

    Backup terms

    • Recovery point objective (RPO). How much recent data may be lost, measured as time before the failure (Source 116).
    • Recovery time objective (RTO). How long the application may be unavailable while it is restored.
    • 3-2-1 rule. Three copies of important data, on two kinds of storage, with one copy off-site (Source 117).
    • Logical and physical backup. A logical backup holds the database's contents (pg_dump). A physical backup holds the database server's files (pg_basebackup).
    Going deeper

    Backups off the server

    MethodWhat it givesRecovery pointUse when
    pg_dump each night, plus pg_dumpall --globals-only for the rolesA snapshot of one database, restored with pg_restore.     pgBackRestFull, differential and incremental backups, compression, encryption, retention rules and a remote repository, built on WAL archiving (Source 120)MinutesPoint-in-time recovery for larger databases, or many backups to manage

    Default. pg_dump each night, copied off the server, when the recovery point is a day or more; pgBackRest when it is minutes.

    Rules for every method:

    • Copy each backup off the database server, to a machine the database server cannot delete from, for example a backup server that pulls the files.
    • Encrypt backups that leave the server, and keep the key apart from the backups.
    • Keep one copy offline or off-site (Sources 117 and 122).
    • Back up what the database does not hold: the roles, the server configuration, and the secrets. The secrets go to the organization's secret store, not with the data.
    • A backup counts only once a restore from it has worked. Restore one before go-live, then every month (Stage 10).
    • Time the backup and the pull against the recovery point: a failure between the dump and the pull loses that dump too.

    D4. Nightly backups, copied off the server

    Do
    1. Check that /var/backups/user-notices on live is postgres:usernotices-backup with mode 2750 (B2).

The private key that decrypts them is kept in the organization's secret store, not on either server.
    5. Have the organization's backup system copy the first backup of each month to offline storage at another site and keep it for a year.
    6. Use PostgreSQL 18's pg_dump. pg_dump must be the same major version as the server or newer.

    Part E

    Choose the deployment strategy

    The deployment strategy decides how a new release replaces the old one, and so how long users are interrupted and how fast a bad release is undone. It comes from the Stage 1 update requirement. This part is the guide's step 9. It follows Part D so that the strategies can be compared with the deploy script there; decide it before the first deploy to live.

    Basics

    Deployment terms

    • Release and deploy. A release is a tested build with a version number. Deploying puts a release on the servers. A feature flag can keep new behavior switched off after the deploy and switch it on later.
    • Promote. Deploy to live the same build that passed in the sandbox.
    • Downtime. Time when users cannot use the application.
    • Instance. One running copy of a service.
    • Rollback. Going back to the previous release after a bad one.
    • Both versions at once. In every strategy except big bang, the old and new versions run at the same time. After any rollback, the old code runs against the new schema. Either way, the database must work with both versions (Stage 7, expand and contract). The same holds for queued jobs: jobs queued by one release are run by the next release's workers, and after a rollback by the previous one's. Change a task's name or arguments the same way: add the new form first, and remove the old one a release later.

import httpx
from app.settings import settings


class NumberNotAllowed(Exception):
    """The number is not in SMS_ALLOWLIST, which is set in the sandbox."""


class HttpSmsClient:
    """Implements SmsClient from app/interfaces/sms.py."""

    def __init__(self, url: str, key: str, allowlist: set[str], client: httpx.Client | None = None):
        self.url, self.key, self.allowlist = url, key, allowlist
        self.client = client or httpx.Client(timeout=10)

    def send(self, phone: str, text: str) -> str:
        # When SMS_ALLOWLIST is not empty (the sandbox), send only to the numbers in it.
        if self.allowlist and phone not in self.allowlist:
            raise NumberNotAllowed(phone)
        response = self.client.post(self.url, json={"to": phone, "text": text},
                                    headers={"Authorization": f"Bearer {self.key}"})
        response.raise_for_status()
        return response.json()["id"]


def make_sms_client() -> HttpSmsClient:
    return HttpSmsClient(settings.sms_api_url, settings.sms_api_key, settings.sms_allowlist_numbers)

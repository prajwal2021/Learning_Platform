Step 1 of 8

Set up Git

Each developer installs Git 2.56, gives Git the name and email that commits will carry, connects to GitHub with an SSH key, and sets the three options from the guide's User Notices example. It is done once per machine and takes about 15 minutes.

Basics

Git terms

  • Repository. The project's files and their full history.
  • Commit. A saved set of changes, with a message and an id (a hash such as 3f2c9a1).
  • Branch. A movable name for a line of commits. main is the shared branch that releases are built from.
  • Remote. The copy of the repository on the hosting service, usually called origin. git push sends commits to it; git fetch and git pull bring commits from it.
  • Pull request. A request to merge a branch into main, where other developers review the change and CI runs the tests.
  • Merge. Combining the changes from two branches. When both changed the same lines, Git cannot choose between them and reports a merge conflict.
  • Tag. A fixed name for one commit, used to mark releases such as v1.4.0.
  • Staging area. The changes chosen for the next commit. git add puts changes there.
  • HEAD. The commit your working copy is on, usually the tip of the current branch.
  • origin/main. Your copy of the remote's main, as of your last git fetch.
  • Force push. A push that replaces the remote branch's commits with yours, used only after a rebase of your own branch.
  • Hotfix. A fix made for the release that is live, while main holds newer work.
Basics

Settings and keys

  • Global setting. A setting stored in ~/.gitconfig by git config --global. It applies to every repository on the machine. A setting made inside a repository without --global is stored in that repository's .git/config and takes precedence there.
  • SSH key pair. Two files. The private key (~/.ssh/id_ed25519) stays on your machine; the public key (~/.ssh/id_ed25519.pub) is added to your GitHub account. GitHub then accepts pushes from a machine that holds the private key.
  • Passphrase. A password that protects the private key file. ssh-agent holds the unlocked key while you work, so you type the passphrase once per session.
  • Conflict style. How Git writes a conflict into a file. With zdiff3, Git also shows the original lines, between a ||||||| line and the ======= line.
  • rerere. Short for reuse recorded resolution. Git records how you resolved a conflict and applies the same resolution if the same conflict appears again (Source 151).
  • Force-if-includes. A check added to a force push: it refuses when the remote branch holds commits that your local branch has never included (Source 149).
Do

  1. Install Git 2.56 and check the version. git-scm.com lists 2.56.0 as the latest release (Sources W12 to W14).

    System Command
    Ubuntu sudo add-apt-repository ppa:git-core/ppa, then sudo apt update and sudo apt install git. Ubuntu 24.04's own package is Git 2.43
    macOS brew install git. The Git in Xcode Command Line Tools may be older
    Windows The Git for Windows installer from git-scm.com, or winget install --id Git.Git -e --source winget

  2. Tell Git your name and the email address on your GitHub account. Every commit records them.

  3. Create an SSH key, start ssh-agent and add the key to it. Press Enter to accept the file name, then type a passphrase twice.

  4. Add the public key to GitHub: Settings, SSH and GPG keys, New SSH key, key type Authentication Key, paste the contents of ~/.ssh/id_ed25519.pub, then Add SSH key (Source W5). From the terminal, gh ssh-key add ~/.ssh/id_ed25519.pub --type authentication --title "work laptop" does the same.

  5. Test the connection with ssh -T git@github.com. The first time, check the ED25519 fingerprint against the one GitHub publishes (SHA256:+DiY3wvvV6TuJJhbpZisF/zLDA0zPMSvHdkr4UvCOqU) before typing yes (Source W6).

  6. Set the three options from the guide's example: merge.conflictStyle zdiff3, rerere.enabled true and push.useForceIfIncludes true.

  7. Check the result with git config --global --list.

  8. Clone the repository with its SSH address, not the HTTPS one: git clone git@github.com:your-org/user-notices.git.

  • git --version prints git version 2.56.0 or later.
  • git config --global --list shows your name, your email and the three settings.

Watch for
  • An older Git. merge.conflictStyle zdiff3 needs Git 2.35 or later, and --force-if-includes needs 2.30 or later. Ubuntu 24.04's own package is 2.43: the commands in this workbook run there, but some messages and hints differ from the output shown.
  • An email GitHub does not know. Commits made with an address that is not on your GitHub account are not linked to you on GitHub. Use the account's address or its noreply address.
  • An HTTPS remote. A clone made from the https:// address asks for a token instead of using the key. Switch it with git remote set-url origin git@github.com:your-org/user-notices.git.
  • A repository setting that hides the global one. git config --show-origin merge.conflictStyle shows which file the value comes from.
  • The private key. It never goes into a repository, a chat or a ticket. If it is exposed, delete the public key on GitHub and create a new pair.
Step 2 of 8

The daily loop

Every change starts on its own branch from an up-to-date main, is committed in small steps, and is pushed for a pull request. After the merge, the branch is deleted. The guide's Steps 1 to 5 and 8 are this loop; its Step 6 (review) is Step 3 here, and its Step 7 (bringing the branch up to date) is Step 5.

Do

  1. Start from an up-to-date main: git switch main, then git pull.

  2. Create one branch per change: git switch -c notice-preview. Name the branch after the change, in lower case with hyphens. Keep it to one change and merge it within a day or two; branches that live for weeks accumulate conflicts. A team that merges many times a day behind feature flags commits to main directly instead, which is called trunk-based development (Source 143).

  3. Commit in small steps. Stage the changes with git add -p, which shows each changed block (a hunk) and asks what to do with it: y stages it, n leaves it out, s splits it into smaller hunks, q stops (Source W16). git diff --staged then shows exactly what the commit will contain. Write a message that says what the change does (the commit message guide is in Templates).

  4. Commit files that belong together in the same commit:

    Change Commit it with
    frontend/package.json frontend/package-lock.json, from the same npm install
    backend/requirements.in backend/requirements.txt, from the same pip-compile
    A model change in app/db/models.py The Alembic migration that applies it (Stage 7)
    A new router in app/routers/ app/main.py, which lists it
    A new setting in app/settings.py backend/.env.example, with the setting's name and a placeholder value

  5. Push and open a pull request: git push -u origin notice-preview, then open the pull request from the branch's page on GitHub (Source 144), or run gh pr create --fill, which takes the title and body from the commits (Source W19). CI runs the tests and the checks.

  6. After the pull request is squash-merged (its commits combined into one commit on main, Step 5) and the branch deleted on GitHub: git switch main, git pull, and git branch -D notice-preview (Source 162). git fetch --prune then removes your copy of the deleted remote branch (origin/notice-preview).

git switch -c notice-preview           # a branch for one change

Step 3 of 8

Pull requests and review

A pull request is where a change is read by a second developer and checked by CI before it reaches main. The pull request template makes every author answer the same questions, CODEOWNERS sends changes under backend/migrations/ to the lead developer, and the reviewer reads the change against the Stage 5 security checklist. The author does not approve their own pull request; GitHub does not allow it (Source W20).

Basics

Review terms

  • Pull request template. A Markdown file at .github/pull_request_template.md. GitHub copies it into the description of every new pull request (Source W8).
  • Code owner. A person listed in .github/CODEOWNERS for a path. GitHub requests their review when a pull request changes that path, and with Require review from Code Owners set (Step 4), one of them must approve. The last line that matches a file decides its owners, and owners need write access to the repository (Source W7).
  • Review. On the Files changed tab, the reviewer comments on lines, then chooses Review changes and one of three outcomes: Comment, Approve or Request changes, and clicks Submit review (Source W9).
  • Required check. A CI job that must pass before the pull request can merge (Step 4).
  • Three-dot diff. git diff origin/main...origin/notice-preview shows what the branch changed since it left main, which is what the pull request shows. With two dots, git log origin/main..origin/notice-preview lists the commits that are on the branch and not on main.
Do

  1. Commit .github/pull_request_template.md and .github/CODEOWNERS on a branch and merge them through a pull request. Both files are in Templates.

  2. As the author, read your own diff on Files changed before you ask for a review, and fill in every section of the template. Tick a checklist item only after checking it; for an item that does not apply, say so in a word after it.

  3. As the reviewer, read every file on Files changed against the ten Stage 5 checks in the table below. Comment on the lines that need a change.

Branch protection

Branch protection is the set of rules GitHub enforces on main: no change arrives except through a pull request with passing checks and the required approvals, and nobody can force push or delete the branch. Stage 4 set the first rules; this step sets all of them, adds the same rule for release branches, and makes squash and merge the only merge method. A repository admin does it once.

Basics

Protection terms

  • Branch protection rule. Rules for every branch whose name matches a pattern, such as main or release-*. Set under Settings, Branches (Source W1).
  • Stale approval. An approval given before the author pushed more commits. With Dismiss stale pull request approvals when new commits are pushed, GitHub removes it.
  • Up to date before merging. The branch must contain the latest commit on main, so the checks ran against the code that will result from the merge.
  • Bypass. Admins can merge past the rules unless Do not allow bypassing the above settings is ticked.
Do

    • Branch name pattern: main

    • Require review from Code Owners (off with one developer)

Step 5 of 8

Merge, squash and rebase

Before a pull request merges, its branch must contain the latest main and pass the tests again. Your own branch is brought up to date with git rebase origin/main; a branch someone else has pulled is brought up to date with git merge origin/main. The pull request is then squash-merged, so main gets one commit per change. When both sides changed the same lines, Git stops with a conflict that you resolve by hand.

Basics

Merging terms

  • Merge commit. A commit with two parents that joins a branch to main. The branch's own commits stay in the history (Source 145).
  • Squash commit. One new commit on main that holds all of a branch's changes. The branch's commits do not reach main (Source 146).
  • Rebase. Replaying your commits, one by one, on top of another commit. Each replayed commit gets a new id, so the remote branch must then be replaced with a force push (Source 147).
  • Fast-forward. Moving a branch name forward to a later commit when no merge is needed, as git pull does on a main with no local commits.
  • Conflict markers. The lines Git writes into a file when it cannot combine two changes: <<<<<<< starts the first side, ||||||| starts the original lines (with zdiff3), ======= separates the sides, and >>>>>>> ends the second side.
  • Behind main. main has commits your branch does not contain. git log --oneline HEAD..origin/main lists them after a git fetch.
Going deeper

Method What happens to the history Use when Avoid when

      Undoing changes

      The right way to undo a change depends on whether it is uncommitted, committed, pushed or merged. Edits not yet committed are discarded with git restore. A commit not yet pushed can be changed with git commit --amend. Anything that has been pushed, and above all anything on main, is undone with git revert, which adds a new commit and leaves the history that others already have in place.

      Basics

      Undo terms

      • Working copy. The files in your folder as you have edited them. git status --short marks a file changed there with M in the second column, and a file staged for the next commit with M in the first column.
      • Restore. git restore throws away the edits to a file that are not staged; when nothing in the file is staged, that puts it back to its last committed version. With --staged, it takes the file out of the staging area instead.
      • Amend. git commit --amend replaces the last commit with a new one. The new commit has a new id.
      • Revert. git revert adds a commit that does the opposite of an earlier one (Source 148).
      • Reset. git reset --hard moves the branch to another commit and makes the working copy match it. Commits left behind are no longer on any branch.
      • Reflog. Git's record of where HEAD has been in your clone. A commit left behind by a reset or an amend is still listed there, by default for 30 days, and can be recovered.

      Watch for

      • Deleting the file but not rotating the key. The key is in the history of every clone that fetched it.
      Step 7 of 8

      Releases and tags

      CI builds every merge to main and deploys it to the sandbox (Stage 9). When a build has passed the sandbox checks and is to go live, the developer who releases tags the commit that build came from, for example v1.4.0, and pushes the tag. The live deploy installs that commit's build into a release folder named 1.4.0. The tag then records, for good, which commit is in release 1.4.0.

      Basics

      Tags and versions

      • Annotated tag. A tag stored as its own object, with the tagger's name, a date and a message, made with git tag -a (Source W15). Release tags are annotated.
      • Lightweight tag. A name for a commit with no message or tagger, made with git tag and no -a. Not used for releases.
      • Version number. User Notices numbers releases major.minor.patch. A fix to a live release raises the last number (1.4.0 to 1.4.1); a release with new features raises the middle one (1.5.0).
      • Pushing a tag. git push sends branches, not tags. Push a tag by name, with git push origin v1.4.0. git push --tags also sends tags, but it sends every tag in your clone.
      Do
      1. Find the commit the release build came from. CI shows it on the build; git fetch then git log --oneline origin/main lists the recent ones.
      2. Tag that commit, by its id: git tag -a v1.4.0 7d41e0b -m "Release 1.4.0".
      3. Push the tag: git push origin v1.4.0.
      4. Check the tag: git show --no-patch v1.4.0 shows the tagger, the message and the commit.
      5. Run the live deploy for that tag (Stage 9). It installs the commit's build into /opt/user-notices/releases/1.4.0/ and points /opt/user-notices/current at it.

      Step 8 of 8

      Hotfixes and cherry-pick

      When the live release needs a fix and main already holds unfinished work for the next release, the fix is made on a release branch created from the live release's tag, released from there, and then copied to main with git cherry-pick -x. Both copies go through a pull request. Figure 5 shows the flow.

      Basics

      Hotfix terms

      • Release branch. A branch created from a release tag, such as release-1.4 from v1.4.0, that receives only fixes for that release. It has the same branch rules as main (Step 4).
      • Cherry-pick. Applying the change made by one commit as a new commit on the current branch (Source 154).
      • -x. The cherry-pick option that adds the line (cherry picked from commit ...) with the original commit's full id to the new commit's message, so the two can be matched later (Source 154). In the test run with Git 2.56.0, the line was kept after a conflicted cherry-pick too; check the message after git cherry-pick --continue.
      • Port. The copy of a fix on another branch; here, the pull request that brings the 1.4.1 fix to main.

      Where a fix for live goes

      Scenario

      A fix for live while main is not ready

      Release 1.4.0 is live. main already holds unfinished work for 1.5, and a bug in 1.4.0 must be fixed today.

      1. Create a release branch from the tag, if it does not exist yet, and push it: git switch -c release-1.4 v1.4.0, then git push -u origin release-1.4. Give it the same branch rules as main.
      2. Branch from it with git switch -c hotfix-1.4.1. Fix the bug, add a test and commit. Note the commit id, for example 5e8d2f7.
      3. Push and open a pull request into release-1.4; it is reviewed like any other change. After the merge, CI builds release 1.4.1 from release-1.4 and deploys it to the sandbox. Once the checks pass, the same build is promoted to live and its commit is tagged v1.4.1.
      4. Bring the fix to main: from an up-to-date main, git switch -c port-hotfix-1.4.1, then git cherry-pick -x 5e8d2f7, push, and open a pull request. The -x option adds a line with the original commit's full id, "(cherry picked from commit 5e8d2f7...)", to the message, so the two commits can be matched later (Source 154). If the fix includes a migration, set its down_revision to main's head in the port, as in Scenario: Two branches each add a migration.
      Do

      The scenario as commands, as run in Lab 6:

      1. Create and push the release branch: git switch -c release-1.4 v1.4.0, then git push -u origin release-1.4. Check that the release-* protection rule from Step 4 covers it.
      2. git switch -c hotfix-1.4.1, fix the bug, add a test, run the tests, commit, and git push -u origin hotfix-1.4.1. Note the commit id (git log --oneline -1); step 5 uses it.
      3. Open the pull request with release-1.4 as the base branch (gh pr create --base release-1.4). After review and Squash and merge, CI builds and deploys 1.4.1.
      4. When the 1.4.1 build has passed the sandbox checks and is to go live, tag the commit it was built from (Step 7). """Schedules and lists notices.

A small copy of the User Notices NoticeService for the Git labs. It keeps
notices in memory; the real service stores them through NoticeStore and
sends them with send_notice.
"""
from dataclasses import dataclass
from datetime import datetime, timezone


@dataclass
class Notice:
    id: int
    group_id: int
    text: str
    send_at: datetime
    status: str = "scheduled"


class NoticeService:
    def __init__(self) -> None:
        self._notices: list[Notice] = []

    def schedule_notice(self, group_id: int, text: str, send_at: datetime) -> Notice:
        """Schedule a notice to a group. The send time may not be in the past."""
        now = datetime.now(timezone.utc)
        if send_at < now:
            raise ValueError("Send time is in the past")
        notice = Notice(len(self._notices) + 1, group_id, text, send_at)
        self._notices.append(notice)
        return notice

    def list_notices(self, group_id: int | None = None) -> list[Notice]:
        """Notices for one group, or for every group, earliest send time first."""
        notices = [n for n in self._notices if group_id in (None, n.group_id)]
        return sorted(notices, key=lambda n: n.send_at)
EOF

          Commit message guide

          From Pro Git's guidelines for commit messages (Source W21):

          1. First line: what the commit does, in the imperative, in 50 characters or fewer: "Reject a notice with no text", not "Rejected a notice with no text" or "Changes to notices".
          2. Then a blank line and, when the change needs one, a body wrapped at 72 characters that says why the change was made and what a reviewer cannot see in the diff.
          3. One change per commit. Leave unrelated edits out with git add -p (Step 2).
          4. With squash and merge, main gets one commit per pull request. GitHub takes its message from the single commit, or, when there are several commits, uses the pull request title with the list of commits as the body (Source W2), so the pull request title follows rule 1 too.

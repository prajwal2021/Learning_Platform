Settle the versions

Stage 3 fixes which release of every tool the application is built on. It also writes two rules: how the application's own API may change, and how quickly updates reach live after launch.

It takes the Stage 2 stack as input and produces a version table with support end dates and the exact version of every dependency, a written breaking-change rule and a patching rule. The versions go into lock files when Stage 4 creates the repository. The running example is User Notices: a Next.js front end and a FastAPI backend on Python, with PostgreSQL, on two Ubuntu Server 24.04 LTS machines, live and sandbox.

Part A

Reading a version number

Basics: Version numbers

The part of a version number that changes tells you how much changed. Most tools follow Semantic Versioning, where a version is MAJOR.MINOR.PATCH:

  • MAJOR. Changes that can break code written against the previous major version.
  • MINOR. New features that keep existing code working.
  • PATCH. Bug fixes that keep existing code working.
  • 0.y.z. A major version of 0 means initial development. Anything may change in any release.

Each tool in the stack applies these rules a little differently, so read each number by its own project's rule.

ToolExampleWhat the parts meanWhat it means for you

PostgreSQL18.618 is the major version, released about once a year. 6 is the minor release, which contains only fixesChoose the major version. Always run its latest minor release

Part A

Part A, step by step: choose each release

Part A is the first five steps of Stage 3 in the guide. Steps 1 to 3 apply to platform components (the operating system, the runtimes, the database and the framework, which publish support policies). Step 4 applies to libraries. Step 5 checks everything together.

  1. List the components. Write down everything from Stage 2 that has a version, in two groups. Platform components: Ubuntu Server, PostgreSQL, Python, Node.js, Next.js, and nginx, which comes from the Ubuntu package. Libraries: FastAPI, SQLAlchemy, Alembic, psycopg, uvicorn (the server program that runs the FastAPI application, added in Stage 4), and anything else installed with pip or npm. Output: an empty version table with one row per platform component. Components added later, such as Redis in Stage 8, join the table when they are added.
  2. Choose each platform component's major version. Open the component's support page and apply three tests to each candidate, in this order:
    • Released for production and supported. A release the project recommends for production use, not past its end of life. A beta or release candidate fails this test. So does a Node.js release in its Current phase, because Node.js says production applications should use only Active LTS or Maintenance LTS releases.
    • Time for fixes. The major version has had several minor or maintenance releases since its first release. A major version released in the last few months has not, and other tools have had less time to test against it.
    • Support left. Among the candidates that pass both tests, prefer the one with the most support remaining.
    Then install the latest minor or patch release of the chosen major version, and record the version, the reason, the support end date and a review date in the version table. For the operating system, choose the LTS release the organization's infrastructure team supports; User Notices runs Ubuntu Server 24.04 LTS. nginx takes the version Ubuntu ships, 1.24, and follows the Ubuntu security updates, so it needs no test of its own.
  3. Compare with what is in use. If the organization already runs an older version of the component, list what was added, changed and removed between the two (see Comparing with what is in use). A version already out of support needs a plan to move off it.
  4. Pin the libraries. Libraries without support policies (FastAPI, SQLAlchemy, Alembic and similar) get an exact version, are pinned in a lock file, and are updated one at a time, with the tests run after each update. For Python, the lock file is a requirements.txt generated by pip-compile from requirements.in, so the libraries' own dependencies are pinned too (see Pinning libraries).
  5. Check compatibility. Confirm that every part supports every other part it touches: the Python version, the packages in the project's virtual environment, the database driver and the database version (see Checking compatibility).

The first two tests remove candidates; the third chooses among what is left. The chosen version goes into the version table with its review date.

What to look for in release notes

  • New minimum requirements. Next.js 16 needs Node.js 20.9 or later. Alembic 1.20 needs SQLAlchemy 2.0 or later.
  • Renamed items. Next.js 16 renamed the middleware file to proxy.
  • Removed items. Next.js 16 removed the next lint command and synchronous access to request APIs such as cookies() and params.
  • Changed defaults. Next.js 16 changed the default image cache time (images.minimumCacheTTL) from 60 seconds to 4 hours.
  • Changes marked breaking. FastAPI 0.143.0 made automatic OpenTelemetry exporter setup opt-in (OpenTelemetry is a library for tracing and metrics).

Part A, step 4

Pinning libraries

A lock file lists the exact version of every package the project installs, including the packages your libraries depend on, so your machine, CI and the server all install the same code. Stage 3 records the versions. Stage 4 writes them into the Python lock file when it creates the repository, and Stage 6 does the same for the front end.

Python: requirements.in and requirements.txt

The backend uses pip-tools. backend/requirements.in lists the libraries the project chooses directly, at their Stage 3 versions. pip-compile reads it and writes backend/requirements.txt, the lock file: every package at an exact version, with a comment naming what pulled it in. requirements.txt is never written with pip freeze and never edited by hand. To change it, change requirements.in and run pip-compile again.

# Stage 4, from the backend folder: create and activate the virtual environment

Scenario: Updating one library

Update one package at a time, so a failure points to one change. Example: a project pinned to FastAPI 0.142.4 when 0.143.0 shipped on October 8, 2026.

  1. Read the release notes between the two versions. FastAPI 0.143.0 lists one breaking change: automatic OpenTelemetry exporter setup became opt-in, and an application that relied on it has to set FASTAPI_OTEL_AUTO_CONFIGURE=true (FastAPI release notes).
  2. Change the pin in requirements.in from fastapi==0.142.4 to fastapi==0.143.0, then run pip-compile requirements.in and pip install -r requirements.txt in the virtual environment.
  3. Run the tests. Fix what fails, or go back to the old pin and record why.
  4. Read the diff with git diff requirements.txt. It should show the package you updated and any packages it pulled in, nothing else.
  5. Commit requirements.in and requirements.txt together, with a message that names the update, for example Update fastapi 0.142.4 to 0.143.0.

Part B

Part B: the breaking-change rule

A change to your API is breaking when a client written against the current version could fail, or behave differently, after the change ships. The URL staying the same does not make a change safe: a renamed field breaks every client that reads it at the same URL.

Ask this of every planned change, and count your own front end as a client.

Two cases that depend on what the written rule promises clients

  • A new value in an existing list, such as a notice status cancelled. A client that handles only the values it knows can fail on it. Either the rule says clients must accept unknown values, or treat the change as breaking.
  • A bug fix that changes visible behavior. If a client could depend on the old behavior, treat it as breaking.

What a breaking change requires

  1. A new version. The old routes keep their behavior; the changed behavior ships under the next version, for example /v2/users/{id}.
  2. Notice before release. Every client owner is told what changes, when /v2 is available, and when the /v1 route stops.
  3. Both versions running. The /v1 and /v2 routes run side by side until the clients have moved.

The version usually sits in the path, /v1/users then /v2/users (Azure: API versioning with Azure API Management).

When the only client is your own front end, released together with the backend, there is a shorter path: ship the backend change and the matching front end change in the same release. User Notices is in this position today. The rule changes the day another system starts calling the API.

Part B

Releasing /v2 alongside /v1

When another system calls the API and a breaking change is needed, the changed route is added under /v2 beside its /v1 route, both run while clients move, and the /v1 route is removed on a date announced in advance. Routes that do not change stay under /v1 only.

The example assumes a reporting system has started calling GET /v1/users/{id}, and User Notices needs to rename phone to phone_number. The notice goes out before /v2 ships, both versions run for the agreed period, and GET /v1/users/{id} is removed only after its sunset date.

Two response models, one service

# app/interfaces/users.py (excerpt)
from pydantic import BaseModel

class User(BaseModel):          # the /v1 response, unchanged
    id: int
    name: str
    phone: str
    group_id: int
    opted_in: bool

class UserV2(BaseModel):        # the /v2 response
    id: int
    name: str
    phone_number: str           # renamed in v2
    group_id: int
    opted_in: bool
# app/routers/users_v2.py
from typing import Annotated
from fastapi import APIRouter, Depends, HTTPException
from app.auth.current_user import current_user
from app.interfaces.auth import Staff
from app.interfaces.users import UserService, UserV2
from app.services.users import get_user_service

router = APIRouter(prefix="/users", tags=["users, version 2"])

CurrentStaff = Annotated[Staff, Depends(current_user)]
UserServiceDep = Annotated[UserService, Depends(get_user_service)]

@router.get("/{user_id}")
async def get_user(user_id: int, staff: CurrentStaff, service: UserServiceDep) -> UserV2:
    try:
        user = await service.get_user(user_id)   # the same service call as v1
    except LookupError as error:
        raise HTTPException(status_code=404, detail="User not found") from error
    return UserV2(id=user.id, name=user.name, phone_number=user.phone,
                  group_id=user.group_id, opted_in=user.opted_in)

Both routers call UserService.get_user; only the shape of the response differs. The main.py index lists both:

# app/main.py (excerpt)
# Users, version 1. GET /v1/users/{id} is deprecated and removed after June 30, 2027: routers/users.py
app.include_router(users.router, prefix="/v1")
# Users, version 2: routers/users_v2.py
app.include_router(users_v2.router, prefix="/v2")

Marking GET /v1/users/{id} as deprecated

Two HTTP response headers tell a client that a route is deprecated and when it will stop working. Deprecation gives the date the route was or will be deprecated (RFC 9745, March 2025). Sunset gives the date it may stop responding (RFC 8594, an Informational RFC, May 2019), and must not be earlier than the Deprecation date. A Link header with rel="deprecation" can point to the migration notes. A deprecated route keeps working exactly as before; the headers are information only.

Removing GET /v1/users/{id}

Before the sunset date, check the request logs for calls to GET /v1/users/{id} and contact the owner of any client still using it. Removing the route is then a normal change: delete get_user and mark_deprecated from routers/users.py, update the route's comment in main.py, then release. The other /v1 routes keep running.

The dates in this example are an illustration. The length of each period is agreed with the client owners and written in the notice.

Part C

Part C: the patching rule

Step 7 of Stage 3 writes down how quickly each kind of update is applied after launch: minor and patch releases of the platform components, security fixes, and library updates, each through the sandbox first. Stage 10 puts the rule on a calendar, with an owner and a monthly update window.

Basics: Update terms

  • Patch release. A release that fixes bugs or security problems without adding features: a change in the last number, such as Next.js 16.0.7. Python calls these maintenance releases.
  • Minor release. A change in the middle number. What it may contain depends on the project: a PostgreSQL minor release, such as 18.6 to 18.7, contains only fixes; a Node.js or Next.js minor release adds features without breaking code; a FastAPI 0.x minor release can contain breaking changes (see Reading a version number).
  • Security advisory. A notice from a project or vendor that describes a vulnerability: which versions are affected, which releases fix it, whether there is a workaround, and how severe it is. Next.js published one for CVE-2025-66478 on December 3, 2025 (Next.js advisory); Node.js announces its security releases on its blog, with the highest severity for each release line (Node.js vulnerabilities).
  • CVE. An identifier, such as CVE-2025-66478, for one publicly disclosed vulnerability, so that advisories, vendors and security tools refer to the same flaw. The CVE Program identifies and catalogs them (CVE Program). Severity is usually a CVSS score from 0.0 to 10.0, and 9.0 to 10.0 is rated critical (FIRST: CVSS v4.0). CVE-2025-66478 was rated 10.0.
  • A flaw reported as being exploited. The advisory, or a list such as the Known Exploited Vulnerabilities catalog of CISA (the United States Cybersecurity and Infrastructure Security Agency), says attackers are already using the flaw (CISA: Known Exploited Vulnerabilities). Under the User Notices rule, this moves the deadline for live from two working days to the same day.
  • Sandbox and update window. The sandbox is a second copy of the deployment, used for testing, set up in Stage 9: a second server, set up like live, where every change goes first. An update window is a fixed time when updates are applied to live; Stage 10 sets a monthly one.

The User Notices patching rule

Patching rule: minor and patch releases of PostgreSQL, Python, Node.js and Next.js go to the sandbox within two weeks of their release, and to live in the first monthly update window after the sandbox checks pass. A security fix rated critical goes to live within two working days, and on the same day when the advisory reports that the flaw is being exploited. Libraries are updated one at a time, with the tests run after each update.

Step 6. The API rule, as committed to the README

## API versioning rule

- Every route starts with /v1.
- A breaking change is any change an existing client could fail on or behave
  differently after: a removed or renamed route or field, a changed type or
  meaning, a new required input, a changed error code, or a changed
  authentication requirement.
- Not breaking: a new optional response field, a new optional input with a
  default, a new route. Clients must ignore response fields they do not use.
- Today the only client is the User Notices front end, released together with
  the backend. A breaking change ships with the matching front end change in
  the same release.
- When another system calls the API, breaking changes go to /v2. Its owner is
  told in writing before release, and /v1 keeps running until the date in the
  notice.

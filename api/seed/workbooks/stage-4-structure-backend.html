Inputs and tools

Step 4.1

Create the repository

Run git init before any file exists and commit .gitignore first, so the .env file is excluded before it is written. This step also pins every dependency in a lock file, commits a .env.example that names every setting, turns on a secret scan that runs before each commit, and gives the code one file to read settings from.

Basics

Secrets

A secret is any value that gives access to something: a password, an API key, a token, a signing key, or a connection string that contains a password. The rules start with the first commit:

  • Secrets live in .env on each developer's machine and in the server's secrets file (Stage 9), never in the code or in any committed file.
  • .env.example lists every setting with a placeholder value, so the names are documented and the values are not.
  • A secret scanner such as gitleaks runs before each commit (Sources 48 and 49), and the repository host's push protection, where it is available, blocks pushes that contain a known kind of secret (Source 50).
  • A secret that reaches a commit is treated as exposed. Rotate it first (Stage 10), then remove it from the files in a new commit. Rewrite the history only when the organization requires it (Working in Git); rewriting does not remove copies already in other clones (Source 51).

A pre-commit hook is a script that Git runs each time you commit. If the script fails, Git does not make the commit. pre-commit is a tool that installs that script and runs the checks listed in .pre-commit-config.yaml (Source W1).

In User Notices, the secrets are the database password inside DATABASE_URL, SESSION_SECRET and SMS_API_KEY.

Steps

  1. Create the project folder and run git init -b main in it, so the first branch is named main.
  2. Write .gitignore at the repository root and commit it.
  3. Create the backend folder and a virtual environment inside it, and install pip-tools and pre-commit into the virtual environment.
  4. Write backend/requirements.in with the libraries chosen in Stage 3, one per line with its version range. Generate the lock file, requirements.txt, with pip-compile, and install from it.
  5. Write backend/.env with the Stage 2 settings and your local values. Write backend/.env.example with the same names and placeholder values. .env.example is committed so others know which settings exist; .env stays on your machine.
  6. Write app/settings.py, the one file that reads settings.
  7. Write backend/.python-version with the Stage 3 Python version, and a short README.md. frontend/.nvmrc is written with the front end in Stage 6.
  8. Write .pre-commit-config.yaml at the repository root and run pre-commit install, so gitleaks scans each commit in this clone. Every developer runs pre-commit install once in each clone.
  9. Commit. These commits stay on your machine until 4.2 pushes them to main. From 4.2 on, every change reaches main through a pull request.

backend/app/settings.py

# app/settings.py
from functools import lru_cache
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    """Every setting the application reads, from the environment or from .env.
    Each name here is also in .env.example."""
    model_config = SettingsConfigDict(env_file=".env")

    database_url: str      # DATABASE_URL
    session_secret: str    # SESSION_SECRET: signs the session cookie
    sms_api_url: str       # SMS_API_URL
    sms_api_key: str       # SMS_API_KEY
    allowed_origin: str    # ALLOWED_ORIGIN: the front end's address, for CORS

@lru_cache
def get_settings() -> Settings:
    """Read the settings once; later calls return the same object."""
    return Settings()

Field names match the names in .env, ignoring case. The .env path is read relative to the folder the service starts in, which is backend/. A missing setting raises a validation error that names it when the settings are first read; the first test, in 4.2, checks this. On the servers, the systemd units load the same names from /etc/user-notices/backend.env (Stage 9), and environment variables take priority over the .env file.

Commit or keep out?

Decide for each file whether it goes into the repository.

Example: a commit that gitleaks blocks

To try the provider's API by hand, a developer writes a scratch script with the provider's test key pasted in, and commits it:

# backend/try_sms.py: trying the provider's API by hand
import httpx

SMS_API_KEY = "<the test key, pasted from the provider's console>"
git add backend/try_sms.py
git commit -m "Try the SMS provider"

gitleaks finds known patterns, not every way of writing a key. In the same test it did not flag the key written as a default in the Settings class (sms_api_key: str = "..."). Check 5 of the Stage 5 security checklist covers what the scanner misses.

Scenario

A key reached a commit

A developer cloned the repository on a new laptop, did not run pre-commit install, and committed backend/try_sms.py with the test key on a branch. On the pull request, CI's gitleaks job (4.2) failed with leaks found: 1 and printed a Fingerprint line that starts with the commit's hash.

  1. Rotate the key first. Create a new key in the provider's console, put it in your .env and in the servers' secrets files, then revoke the old key; Stage 10 has the routine. Until the old key is revoked, anyone with a copy of the commit can use it (Sources 48 and 51).
  2. Remove the file in a new commit on the same branch: 
    git rm backend/try_sms.py
git commit -m "Remove the scratch script"
git push
    CI's gitleaks job still fails, because it reads every commit on the branch and the earlier commit still holds the key.
  3. Record the finding as handled. Copy the Fingerprint line from the CI log into .gitleaksignore at the repository root, with a comment that says when the key was revoked, and commit it: 
    # Test SMS key committed on the try-sms branch; revoked at the provider on 2026-10-15.
af5d4b6a890d0532923e6e5394f6b258c9c64bfe:backend/try_sms.py:generic-api-key:4
    The fingerprint names one commit, file, rule and line, so gitleaks skips only that finding. A key added anywhere else still fails the check.
  4. Push. The gitleaks check passes, and the pull request is reviewed and merged as usual.
  5. Rewrite the history only when the organization requires it (Working in Git). Rewriting does not remove copies already in other clones (Source 51).

The same steps apply when the committed file is .env: change every key it held, then remove it with git rm --cached backend/.env.

Check

  • From the repository root, git check-ignore -v backend/.env prints the .gitignore line that excludes it.
  • git status lists neither .env nor .venv.
  • git ls-files lists backend/.env.example, backend/requirements.in, backend/requirements.txt and .pre-commit-config.yaml.
  • Every library line in requirements.txt has an exact version (==).
  • From backend/, .venv/bin/python -c "from app.settings import get_settings; print(get_settings().allowed_origin)" prints http://localhost:3000.
  • A commit prints Detect hardcoded secrets followed by Passed.

Common mistakes

  • Writing .env before .gitignore exists, so the first git add includes it.
  • Putting real values in .env.example.
  • Committing the .env file. If it happens, change every key it held, then remove it from the repository (Scenario: A key reached a commit).
  • Committing package.json or requirements.in without its lock file, so each install resolves different versions.
  • Writing requirements.txt with pip freeze or editing it by hand, so it no longer matches requirements.in.
  • Installing a library with pip install without adding it to requirements.in, so it is missing from requirements.txt and from every other machine.
  • Committing in a new clone before running pre-commit install, so no scan runs there. CI's gitleaks job still scans every commit (4.2).

Step 4.2

Set the branch rules and CI

Push the repository to GitHub, protect main, and add a CI workflow whose checks main requires. After this step, every change reaches main through a pull request that passes gitleaks, pip-audit and the backend tests.

Basics

Branches, pull requests and checks

  • A branch is a named line of commits. main holds the reviewed and tested code; each change is made on its own short-lived branch.
  • A pull request asks to merge a branch into main. It shows the changes, the checks that ran on them, and the reviews.
  • CI (continuous integration) is the set of checks the hosting service runs on every push. On GitHub, a workflow file in .github/workflows/ lists jobs, and each job reports a check that passes or fails.
  • A required check must pass before a pull request can be merged.
  • A protected branch has rules that GitHub enforces, such as requiring a pull request and passing checks before merging. GitHub blocks force pushes to protected branches by default (Source 59).
  • A force push replaces the history of a branch on GitHub. On main it would remove commits that other people already have.
  • An approval is a review that accepts a pull request. The author of a pull request cannot approve it (Source W6).

Steps

  1. Create an empty repository on GitHub for the organization, without a README, license or .gitignore, so the first push is accepted as it is.
  2. Add it as the remote and push main.
  3. Protect main with the settings in the checklist below. Leave the required checks for step 5: GitHub can require a check only after it has completed successfully in the repository within the past seven days (Source W5).
  4. On a branch, add .github/workflows/ci.yml, .github/pull_request_template.md, .github/CODEOWNERS and the first test. Push the branch and open a pull request; the three CI checks run on it.
  5. When the checks pass, review the pull request against the Stage 5 security checklist and merge it. Then edit the rule for main and add gitleaks, pip-audit and tests as required checks.
  6. From then on, every commit, including the one at each checkpoint, goes on a short-lived branch with one change. If branches and pull requests are new to you, read Working in Git before Stage 5.

.github/workflows/ci.yml

# .github/workflows/ci.yml
name: CI

on:
  push:
  pull_request:

permissions:
  contents: read

jobs:
  gitleaks:
    runs-on: ubuntu-24.04
    env:
      GITLEAKS_VERSION: "8.30.1"
      GITLEAKS_SHA256: "551f6fc83ea457d62a0d98237cbad105af8d557003051f41f3e7ca7b3f2470eb"
    steps:
      - uses: actions/checkout@v7
        with:
          fetch-depth: 0   # every commit, so a key added and later removed is still found
      - name: Install gitleaks
        run: |
          curl -sSfL -o gitleaks.tar.gz "https://github.com/gitleaks/gitleaks/releases/download/v${GITLEAKS_VERSION}/gitleaks_${GITLEAKS_VERSION}_linux_x64.tar.gz"
          echo "${GITLEAKS_SHA256}  gitleaks.tar.gz" | sha256sum -c -
          tar -xzf gitleaks.tar.gz gitleaks
      - name: Scan every commit
        run: ./gitleaks git --redact --verbose

  pip-audit:
    runs-on: ubuntu-24.04
    defaults:
      run:
        working-directory: backend
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-python@v7
        with:
          python-version-file: backend/.python-version
      - run: python -m pip install pip-audit==2.10.1
      - run: pip-audit -r requirements.txt

  tests:
    runs-on: ubuntu-24.04
    defaults:
      run:
        working-directory: backend
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-python@v7
        with:
          python-version-file: backend/.python-version
          cache: pip
          cache-dependency-path: backend/requirements.txt
      - run: python -m pip install -r requirements.txt
      - run: python -m pytest
  • The three jobs report the checks gitleaks, pip-audit and tests, the names that main requires.
  • gitleaks: fetch-depth: 0 fetches every commit, so the scan finds a key that was committed and later removed, or committed in a clone without the pre-commit hook. The job checks the downloaded release against the SHA-256 sum published with it.
  • pip-audit: checks each library pinned in requirements.txt against known vulnerabilities, and fails when it finds one (Source W3).
  • tests: installs requirements.txt and runs python -m pytest from backend/. pytest fails when it collects no tests, so the job needs at least one test before Stage 5; test_settings.py is that test.
  • python-version-file reads backend/.python-version, so CI runs the project's Python version.
  • The jobs run on GitHub's Ubuntu 24.04 runners. Stage 6 adds the front end checks, Stage 7 the integration tests, and Stage 9 the end-to-end tests, the release build and the deploy to the sandbox (a second copy of the deployment, used for testing, set up in Stage 9).
  • To update gitleaks, change GITLEAKS_VERSION and GITLEAKS_SHA256 here and rev in .pre-commit-config.yaml in the same pull request.

backend/tests/test_settings.py, the first test

# tests/test_settings.py
import pytest
from pydantic import ValidationError
from app.settings import Settings

TEST_VALUES = {
    "DATABASE_URL": "postgresql+psycopg://user:password@localhost:5432/test",
    "SESSION_SECRET": "test-only",
    "SMS_API_URL": "https://sms.test/v1",
    "SMS_API_KEY": "test-only",
    "ALLOWED_ORIGIN": "http://localhost:3000",
}

def set_test_values(monkeypatch):
    for name, value in TEST_VALUES.items():
        monkeypatch.setenv(name, value)

def test_settings_are_read_from_the_environment(monkeypatch):
    set_test_values(monkeypatch)
    settings = Settings(_env_file=None)  # ignore any local .env
    assert settings.allowed_origin == "http://localhost:3000"

def test_a_missing_setting_is_named(monkeypatch):
    set_test_values(monkeypatch)
    monkeypatch.delenv("SMS_API_KEY")
    with pytest.raises(ValidationError, match="sms_api_key"):
        Settings(_env_file=None)

The tests set their own values, so they pass in CI, where there is no .env file, and on a machine with one.

Common mistakes

  • Keeping a branch open for weeks with several changes on it. Each branch holds one change and is merged within a day or two (Working in Git).

Step 4.3

Choose the pattern

User Notices uses the layered pattern: routers receive requests, services do the work, and the data layer talks to the database. A call goes down one layer at a time and the result comes back up; no layer calls the layer above it. Write the pattern and the table below into the design document before creating any folder.

What each layer does

LayerFolderDoesDoes not
Routerrouters/Reads the request; checks the body against a Pydantic model; receives injected dependencies; calls one service function; returns the response and status codeRun SQL, call the SMS provider, or apply business rules
Serviceservices/Applies the business rules; calls the data layer and external services; raises an error when a rule failsRead the HTTP request or build the HTTP response
Data layerdb/Reads and writes rows through the database session; returns Pydantic modelsApply business rules or call external services
Authauth/Checks credentials, issues tokens, identifies the signed-in staff memberRead or change users or notices
Interfacesinterfaces/Declares the functions each layer offers: names, inputs, return types, errorsContain working code

Errors cross the layers in one direction. A service raises a plain Python error (ValueError for a broken rule, LookupError for a missing record), and the router turns it into an HTTP status (400, 404). HTTP stays in the routers, so a service can also be called from a test or, in Stage 8, from a task-queue job.

Step 4.4

Create folders by role

Group the Stage 1 screens into areas, then give each area one file in each role folder it needs. User Notices has three areas (sign-in, users, notices), one external service (the SMS provider) and a data layer.

Steps

  1. Group the screens into areas. An area is a set of screens that work on the same data. Users list and User detail both work on users, so they form one area.
  2. Give each area a router file, and a service file if it has business rules. Sign-in has no service file; its logic goes in auth/.
  3. Give each external service its own service file, so no other file calls the provider directly.
  4. Put the data layer in db/: session.py for the connection now, models.py for the tables in Stage 7.
  5. Give each area an interface file in interfaces/, written in 4.5.
  6. Keep tests/, which 4.2 created for the first test. Stage 5 adds a test for each function.
  7. Create only the roles the application has today. A folder for task-queue jobs, for example, is added in Stage 8, and only if the load test calls for a queue.

    Step 4.5

    Write the interfaces

    An interface lists a set of functions with their names, inputs, return types and errors, and no bodies. The Stage 5 skeleton copies these signatures, the assistant fills the bodies against them, and the unit tests check them. In Python, write each interface as a typing.Protocol class in the area's file in interfaces/, or as stub functions with type hints and a docstring, as app/auth/ does for sign-in.

    Steps

    Work through the screens one action at a time.

    1. Take one thing a user does on a screen, for example scheduling a notice on New notice.
    2. Name the function after the action: schedule_notice.
    3. List the inputs the action needs, with their types: text: str, group_id: int, send_at: datetime, author_id: int.
    4. Decide what it returns. Return a Pydantic model such as NoticeSummary, not a database row, so the interface does not depend on the Stage 7 tables.
    5. Write the errors in the docstring: which inputs it rejects and which error it raises.
    6. Add the function to the Protocol class for its area.
    7. Give the data layer an interface too. The service calls a NoticeStore, never PostgreSQL directly, so the Stage 5 stub and the Stage 7 database can each stand behind it.
    8. Fill in the screen-to-interface table. An empty cell is a missing function.

    How a Protocol works

    A Protocol class declares methods without bodies. Any class with methods of the same names and signatures satisfies it, without inheriting from it. In Stage 5 the Notices class in services/notices.py satisfies NoticeService, and InMemoryNoticeStore in tests/stubs.py satisfies NoticeStore. get_notice_service (4.6) is declared to return a NoticeService, so from Stage 5 on a type checker such as mypy reports any difference between the Notices class and the interface. mypy needs its pydantic plugin (plugins = pydantic.mypy) to read the Settings class.

    # app/interfaces/notices.py
from datetime import datetime
from typing import Protocol
from pydantic import BaseModel

class NewNotice(BaseModel):
    """What the New notice page sends."""
    text: str
    group_id: int
    send_at: datetime  # timezone-aware, UTC

class NoticeSummary(BaseModel):
    id: int
    text: str
    send_at: datetime
    status: str  # scheduled, sending, sent or failed

class Recipient(BaseModel):
    user_id: int
    phone: str

class NoticeService(Protocol):
    async def schedule_notice(self, text: str, group_id: int,
                              send_at: datetime, author_id: int) -> NoticeSummary:
        """Store a notice with status scheduled. Sends nothing.
        Raises ValueError for empty text, an unknown group or a past send time."""
        ...

    async def list_notices(self, limit: int = 50) -> list[NoticeSummary]:
        """Newest first, at most limit notices."""
        ...

    async def send_notice(self, notice_id: int) -> None:
        """Send the notice to the users in its group.
        Raises LookupError if the notice does not exist."""
        ...

class NoticeStore(Protocol):
    """Notice data: an in-memory stub in Stage 5, PostgreSQL from Stage 7."""
    async def group_exists(self, group_id: int) -> bool: ...
    async def add_notice(self, text: str, group_id: int,
                         send_at: datetime, author_id: int) -> NoticeSummary: ...
    async def get_notice(self, notice_id: int) -> NoticeSummary | None: ...
    async def list_notices(self, limit: int) -> list[NoticeSummary]: ...
    async def list_recipients(self, notice_id: int) -> list[Recipient]: ...
    async def set_status(self, notice_id: int, status: str) -> None: ...

from typing import Protocol
from pydantic import BaseModel
from app.interfaces.auth import Staff

class Group(BaseModel):
    id: int
    name: str

    """One row of the Users list."""
    id: int
    name: str
    phone: str
    group_id: int
    opted_in: bool

    """One user, as the User detail page shows it."""

    """Fields the User detail page can change. A field that is not sent is not changed."""

    phone: str | None = None
    opted_in: bool | None = None

class UserService(Protocol):
    async def list_groups(self) -> list[Group]:
        """Every group, by name. Used by the group filter and the New notice form."""
        ...

    async def list_users(self, group_id: int | None = None) -> list[UserSummary]:
        """Users in one group, or all users when group_id is None."""
        ...

    async def get_user(self, user_id: int) -> User:
        """Raises LookupError if the user does not exist."""
        ...

    async def update_user(self, user_id: int, changes: UserUpdate, staff: Staff) -> User:
        """Apply the changes, record who made them, and return the updated user.
        Raises LookupError for an unknown user,
        PermissionError unless staff.role is editor."""
        ...

    List rows are UserSummary; the detail page gets User, which adds updated_at. update_user takes the signed-in staff member, so the service can check the role and record who made the change in audit_log (Stage 7). UserUpdate holds only the fields a caller may change, so a request cannot move a user to another group (check 2 of the Stage 5 security checklist). The data layer for users follows the same shape as NoticeStore: a UserStore Protocol with the reads and writes these functions need.

from typing import Annotated
from fastapi import APIRouter, Depends, HTTPException
from app.auth.current_user import current_user
from app.interfaces.auth import Staff
from app.interfaces.notices import NewNotice, NoticeService, NoticeSummary
from app.services.notices import get_notice_service

router = APIRouter(prefix="/notices", tags=["notices"])

CurrentStaff = Annotated[Staff, Depends(current_user)]
NoticeServiceDep = Annotated[NoticeService, Depends(get_notice_service)]

@router.post("", status_code=201)
async def create_notice(body: NewNotice, staff: CurrentStaff,
                        service: NoticeServiceDep) -> NoticeSummary:
    try:
        return await service.schedule_notice(body.text, body.group_id,
                                             body.send_at, author_id=staff.id)
    except ValueError as error:
        raise HTTPException(status_code=400, detail=str(error)) from error

A group can hold 5,000 users, and there are 60,000 user records.Fix nowlist_users takes limit and offset, and the router rejects a limit above the maximum page size (check 10 of the Stage 5 security checklist). The Users list call becomes GET /v1/users?group={id}&limit=50&offset=0.
    Neither send_notice nor list_recipients says whether users who have not opted in receive a notice.Fix nowBoth docstrings state that only users with opted_in true are included.
    Stage 1 requires one send record per message, kept as a log, and no interface writes it.Fix nowNoticeStore gets record_message, called once per message.
    send_notice sends up to 5,000 messages inside one request.Stage 8The load test measures it. If sending moves to a task queue, send_notice keeps its signature.
    Nothing starts a scheduled notice at its send time.Stage 8A scheduler finds the notices due to send, using the (status, send_at) index added in Stage 7.
    Users and notices share one service and one database, so a fault in one area affects the other.Reject150 staff accounts and 40 concurrent requests. One service and one database meet that load, and a second service is one more thing to deploy and maintain.

    Self-check

    Self-check answers explained

    Questions 1 to 4 are the guide's Stage 4 self-check; 5 and 6 are added here. Answer each one, then open it to compare.

    1The users router and the notices router both need the staff member who is signed in. Is that dependency injection or an import?

    Answer. Dependency injection. current_user reads the session cookie of the request being handled, so its result is different for every request. Both routers declare it with Depends(current_user), and FastAPI runs it before each endpoint (4.6, Figure 6).

    2Both routers use a helper that formats phone numbers. Dependency injection or an import?

    Answer. An import. The helper takes a string and returns a string; nothing in it depends on the request or on configuration (Figure 6).

    3A new developer has to fix how notices are scheduled. Where do they start reading?

    Answer. main.py. The comment above the notices router names routers/notices.py, where create_notice receives the request, and services/notices.py, where schedule_notice applies the rules (4.7, Figure 7).

    4A teammate's install produced different front end package versions from yours, although package.json is the same. What is missing, and which command installs exactly what it records?

    Answer. package-lock.json, either not committed or not used. package.json holds version ranges, so each npm install can resolve different versions. Commit package-lock.json and install with npm ci, which installs exactly what the lock file records and stops with an error if it disagrees with package.json (Going deeper: Key project files; Source 57).

    5A teammate wants to call the SMS provider from routers/notices.py to save a file. What do you tell them?

    Answer. Routers do not call external services (4.3). The call goes in services/sms.py behind SmsClient, so the provider's details stay in one file and a test can use FakeSmsClient instead (Figure 5).

    6Why does schedule_notice return a NoticeSummary instead of a database row?

    Answer. The interface is written before the tables exist. A Pydantic model keeps the routers and tests independent of the Stage 7 tables, and FastAPI returns it as JSON (4.5).
